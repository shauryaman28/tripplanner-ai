# DECISIONS.md

> One-line-per-decision log. Updated after each phase.
> A decision is not "we used X" — it is "we chose X **over Y because Z**."

---

## Phase 6 — FlightAgent: One Agent, One Tool

1. **LangGraph node contract:** every node receives a `TripState` (TypedDict) and returns a `TripState`. Partial updates merge via `{**state, **updates}` — nodes only need to return the fields they change. This is LangGraph's native state-merge behavior, not a custom pattern.

2. **No LLM in Phase 6 search node:** `search_flights_node` is a pure function — structured input → MCP call → structured output. We deliberately avoided wrapping this in an LLM call because structured inputs don't need interpretation, and adding an LLM here would introduce latency and hallucination risk for zero benefit.

3. **MCP client as singleton subprocess:** the MCP server runs as a child process (stdio transport) with one persistent `ClientSession`. The session is lazily initialized on first `call_tool()` and reused for the process lifetime. This avoids subprocess spawn overhead on every tool call. Cleanup is wired into FastAPI's lifespan shutdown.

4. **`ToolError` as Pydantic model, never raw exceptions:** `call_tool()` catches all exceptions and returns a `ToolError` model. Agent nodes check `hasattr(result, "code")` to detect errors. This means agents never crash from MCP failures — they populate `state["error"]` instead.

5. **`agent_runs` as the debugging table:** every agent execution writes one row with `input`, `output`, `duration_ms`, and `status` as JSONB. This is intentionally over-logging — when the re-planning logic breaks in Phase 10+, we query `agent_runs` for the trip and read every decision without writing additional logging code.

## Phase 7 — Conditional Edges: Ask Instead of Assume

6. **Router is deterministic — no LLM in the routing decision.** The `router()` function is a plain Python function that checks `state.get(field)` for required fields and returns `"search"` or `"clarify"`. This is explicitly implemented as a LangGraph conditional edge, not a node with an LLM call. Reason: routing logic is simple boolean checks. An LLM here would add latency, cost, and non-determinism for a decision that is fully specified by data presence.

7. **`clarify_node` is also deterministic — no LLM.** It returns a hardcoded question based on which field is missing first. We chose this over an LLM-generated question because: (a) the question set is small and known, (b) deterministic questions are unit-testable without mocking, (c) response time is instant.

8. **Intent parsing uses Gemini Flash at temperature=0.** For extracting structured fields from free text, we use Gemini Flash (model ID from the `GEMINI_MODEL` setting — see #57) with `temperature=0` to maximize determinism. The prompt demands JSON-only output with null for missing fields. Markdown fence stripping handles the model's tendency to wrap JSON in ` ```json ``` ` blocks.

9. **`not state.get(field)` over `field not in state` for retry correctness.** After the first `/plan` returns a clarification, saved state has keys with `None` values (e.g., `{"date": None}`). The original `field not in state` check treats this as "field exists" and skips it on retry — causing an infinite clarification loop. Changed to `not state.get(field)` which treats `None` as "fill this in."

10. **Conversation state in Redis, not Postgres.** Planning state and conversation history are stored in Redis with 24h TTL (matching JWT expiry). Rationale: this is ephemeral session data that expires when the auth token does. Postgres is for durable data (trips, itineraries, agent_runs). Redis gives sub-millisecond reads during the multi-turn clarification loop without polluting the relational schema.

## Phase 8 — HotelAgent & ActivitiesAgent

11. **HotelAgent uses a fresh prompt — not copied from FlightAgent.** Hotel search requires fundamentally different field semantics: `check_in`/`check_out` vs. a single `date`; `budget_per_night` (per room per night) vs. total `budget`; `guests` vs. `passengers`. Copying the flight prompt and renaming fields produces subtle extraction bugs that are hard to catch in mocked unit tests but visible in production (e.g. LLM interprets "departure date" as check-out, or divides budget incorrectly). Starting fresh eliminated 2 of 5 test failures that appeared when a shared prompt was tried first.

12. **ActivitiesAgent router requires BOTH `destination` AND non-empty `interests`.** Unlike FlightAgent (destination, date, budget) and HotelAgent (destination, check_in, check_out, budget_per_night), the activities router treats an empty `interests` list identically to `None`. Rationale: calling `get_attractions` with an empty interests list produces a near-useless query ("top  attractions in Goa") that returns generic sightseeing results regardless of what the user actually wants. Forcing the clarification produces a better result than silently falling back to generic.

13. **Non-English interests pass through to the MCP tool unchanged at the agent layer.** The `intent_parsing_node` instructs Gemini Flash to translate non-English interests (e.g. Hindi "खाना" → "food") when processing `raw_input`. However, `get_attractions_node` does NOT validate or filter interests — it passes whatever is in state directly to the MCP tool, which maps each interest to OpenTripMap `kinds` (an interest it does not know falls back to `interesting_places`). This is intentional: the agent layer should not own language concerns; the MCP tool is the correct boundary. The documented failure mode is "fewer or less relevant results" rather than a crash, and the test `test_non_english_interest_passes_through_without_crash` verifies this contract.

14. **Each agent owns its own independent TypedDict state — no shared monolith.** `HotelState` and `ActivitiesState` are separate TypedDicts rather than one merged `TripState` covering all agents. This keeps each agent self-contained and unit-testable without needing to mock fields irrelevant to it. The OrchestratorAgent (Phase 9) will extract and pass only the relevant state slice to each sub-agent, acting as the state coordinator. Merging all fields into one TypedDict now would make every agent implicitly dependent on every other agent's field set.

## Phase 9 — Orchestrator: Decomposition & Fan-Out

15. **`asyncio.gather` over LangGraph `Send` API for concurrent fan-out.** LangGraph's `Send` API is designed for dynamic fan-out to the same node type with different inputs. For three different agent types (FlightAgent, HotelAgent, ActivitiesAgent) with different state shapes, `Send` requires compiled subgraphs and makes merge logic significantly more complex. `asyncio.gather(return_exceptions=True)` gives identical wall-clock concurrency (all three sub-agents start in the same event loop iteration), simpler error handling per-result, and unit tests that need no LangGraph infrastructure. Concurrency is verified by overlapping `agent_runs.created_at` timestamps in integration tests.

16. **`publish_fn` injected into `OrchestratorState` rather than importing Redis directly in the agent.** The Orchestrator publishes SSE progress events via an async callable passed in by the route. This keeps the agent layer infrastructure-agnostic — unit tests pass a plain `AsyncMock` with no Redis setup. The route creates the closure over the Redis client before calling `agent.run()`. The pattern is the same as the `db` and `trip_id` injection used by sub-agents since Phase 6, keeping all agents consistent.

## Phase 10 — Budget Conflict & Re-Planning

17. **Sequential flight → budget check → hotel+activities over concurrent fan-out.** Phase 9's `fan_out_node` ran all 3 agents concurrently. Phase 10 splits this into `run_flight_node → budget_decision_node → hotel_activities_node`. The extra sequential step is justified: (a) hotels need `remaining_budget` as their nightly cap, not the full trip budget; (b) if the budget check fails we skip hotel + activities API calls entirely; (c) flights are typically the costliest and most variable line item.

18. **`make_budget_decision()` as a pure function.** All threshold logic, cap enforcement, and percentage calculations live in a zero-I/O function. The LangGraph node wraps it with DB logging. This means 10 budget-decision tests run with zero mocks — the fastest and most trustworthy kind.

19. **Thresholds: 35% / 50% remaining.** `< 35%` remaining → escalate; `35–49%` → replan; `≥ 50%` → continue. These satisfy both acceptance criteria: ₹40k budget / ₹28k flights (30% remaining) → escalate; ₹40k / ₹16k (60% remaining) → continue. The 35% floor ensures at least ₹14,000 remains on a ₹40k budget — enough for a 5-day trip at ₹1,000/night hotels + ₹500/day activities.

20. **Replan budget reduction: 65% → 55% of original.** On attempt 1 the flight budget cap drops to 65% (finds connecting/budget-carrier options); on attempt 2 to 55% (last resort). `replan_attempts` is incremented in `budget_decision_node` before routing so `run_flight_node` sees the correct attempt number and applies the right cap via `replan_flight_budget()`.

## Phase 11 — Evaluator Agent: Self-Checking

21. **EvaluatorAgent's four core checks are pure functions, not Claude Haiku calls.** The roadmap frames the Evaluator as an LLM-based independent check. We deliberately implemented `date_out_of_range`, `budget_mismatch`, `duplicate_activity`, and `hallucinated_activity` as deterministic Python functions instead. These are objectively verifiable conditions — date comparison, arithmetic within a tolerance, set membership, duplicate detection — and don't benefit from LLM subjectivity. An LLM call here would add cost, latency, and non-determinism for zero benefit, and would make the "4 known-bad fixtures caught with correct failure type" acceptance criterion dependent on mocked LLM output rather than genuinely-tested logic. This mirrors the Phase 7 router (#6) and Phase 10 `make_budget_decision()` (#18) precedent already established in this codebase. Claude Haiku 4.5 remains the right tool for genuinely subjective quality judgments — the roadmap's own Phase 33 eval-suite grader is that home.

22. **Evaluator is not wired into `orchestrator.py` in Phase 11.** The roadmap places the Evaluator between ItineraryBuilder's draft output and final persistence — but ItineraryBuilder is Phase 12 and doesn't exist yet. Rather than build throwaway integration glue now (mocking a builder that doesn't exist) and rewrite it next phase, Phase 11 ships `EvaluatorAgent` as a fully standalone, fully-tested module validated against the exact draft-itinerary JSON schema Phase 12's roadmap entry defines. Wiring into the graph's conditional edges happens in Phase 12 alongside the builder node it needs to sit after.

23. **`get_retry_chain()` derives attempt numbers from `created_at` ordering — no new DB column.** Rather than add a `retry_count` column to `agent_runs` (which would need an Alembic migration and would duplicate information already recoverable from row order), `get_retry_chain()` reconstructs per-agent attempt numbers by counting occurrences of each `agent_name` in chronological order. This keeps Phase 11 a zero-migration phase while still satisfying "retry is visible" in `GET /trips/{id}/runs`-style queries.

## Phase 12 — Itinerary Builder: Claude Haiku + Structured Synthesis

24. **ItineraryBuilder validates data scope and budget math deterministically in Python, not via LLM self-report.** Mirrors the #21 evaluator precedent, but here the checks run *inside* the builder before the draft ever reaches EvaluatorAgent — cheaper to fail fast on a malformed draft than to round-trip it through a second LLM call first.

25. **Builder failures with no draft share the Evaluator's retry cap.** Rather than a separate half-built failure lane, `route_after_evaluator` treats "no draft produced" as an automatic retry (bounded by `MAX_EVALUATOR_RETRIES`), keeping one retry cap for the whole build+evaluate loop instead of two independent caps that could double the effective retry budget.

26. **Evaluator retry dispatch reruns only the implicated sub-agent** (`flight_agent` or `activities_agent`, via `next_agent_for_failures()`) and loops directly back to `build_itinerary_node`, skipping `budget_decision`/`hotel_activities` entirely. Cheaper than re-deriving unrelated data, and matches the roadmap's "loop back to the relevant agent" wording literally.

27. **Itinerary persistence is one non-branching node (`persist_node`) using a single `AsyncSession` and a single `commit()`.** The itinerary row and the trip-status update are queued on the same session and committed together — a failure before commit leaves neither write applied (verified in `test_phase12_integration.py`). `generate_embeddings()` runs as a same-node call rather than a FastAPI `BackgroundTask` because there is no request context inside the orchestrator; Phase 14 revisits this boundary when it implements real embedding generation. *(Superseded by #53: embeddings are now spawned as a background task.)*

## Phase 13 — Persistence: Storing Every Run

28. **Four previously-silent orchestrator nodes now log `agent_runs` rows: `intent_parsing_node`, `persist_node`, `escalate_node`, `builder_failed_node`.** `merge_node` is intentionally excluded — it is a pure publish step (fires the `planning_complete` SSE event) with no decision-making. Adding a row there would add noise without diagnostic value. The minimum row count per happy-path run is 9; all paths exceed the roadmap's "≥ 7" criterion. `GET /trips?status=` filter and `GET /trips/{id}/timeline` are added to the trips router in the same phase so the stored rows are immediately queryable and human-readable.

## Phase 14 — Embedding Generation: OpenAI text-embedding-3-small

29. **Two embedding rows per itinerary (full-text + structured summary), not one.** A single vector averaging all content works for recall but gives poor precision for the Phase 23 similarity search use case. The second row — a compact `"{destination} N days M INR {budget_range}. Top activities: …"` string — produces a much stronger similarity signal for "find me a trip like this" queries because it encodes the high-level trip profile rather than raw activity text. The cost is one extra OpenAI API call per itinerary (negligible at $0.00002/1k tokens). The two-row design is established now so the Phase 23 query can choose which embedding type to use.

30. **`generate_embeddings()` opens its own `AsyncSessionLocal` rather than reusing the orchestrator's session.** `persist_node` commits the itinerary and immediately closes its transaction. If `generate_embeddings()` were called on the same session after the commit, it would operate on a closed transaction context. By opening a fresh session, the embedder is independent of the caller's lifecycle and can be safely called from startup recovery, background tasks, or any other context without coordination.

31. **`pending_retry` row as the graceful-degradation signal — not a raised exception.** When OpenAI fails after all tenacity retries, the embedder writes one row with `embedding_model="pending_retry"` and `vector=NULL`, then commits it. The trip status remains `completed` — a missing vector is a degraded but not broken state. The startup recovery in `main.py` re-queues these rows on next boot, making recovery automatic with zero operator intervention. Raising an exception here would surface a non-fatal embedding failure to the planning pipeline, potentially marking a fully-valid itinerary as `failed`.

## Phase 15 — Multi-Turn Refinement

32. **`turn` is an integer column (not a foreign key, not an enum) because conversation turns are naturally 1-indexed integers and the primary query pattern is `WHERE turn = N`.** A foreign key to a `turns` table would add a join for every `/runs` query with no benefit — the turn number is already self-describing. A `SERIAL` or enum would over-engineer a simple counter. The composite index `(trip_id, turn)` makes `GET /trips/{id}/runs?turn=N` index-only for the common case.

33. **`RefinementClassifier` uses Gemini Flash at `temperature=0`, not a rule-based classifier.** A rule-based classifier (keyword matching) would need constant maintenance as users rephrase requests. LLM classification at temperature=0 generalises across languages and phrasings. Hard rules are embedded in the prompt (not code) so they can be updated without deployments. The fallback to `full_replan` on any parse failure means a buggy LLM response never corrupts the state — it just triggers a safe full re-run.

34. **`OrchestratorAgent.refine()` does NOT run the LangGraph — it calls nodes directly in a short inline loop.** Running the full graph for a targeted refinement would re-execute `intent_parsing_node` and `budget_decision_node`, which are irrelevant when only one agent needs to re-run. The inline approach (`targeted_agent → build_itinerary_node → evaluate_node → retry loop → persist_node`) is ~40 lines versus rebuilding a parameterised sub-graph in LangGraph. For targeted refinements the overhead of graph compilation is not worth it; the full graph is still used for `full_replan` and `add_day`. *(Refined by #55: what each refinement type actually changes.)*

35. **`persist_node` always INSERTs a new `Itinerary` row per turn — it never UPDATEs.** This preserves the full planning history: turn 1 and turn 2 itineraries both exist in the DB with different `created_at` timestamps. `GET /trips/{id}/itinerary` returns the latest by `created_at` (existing behaviour unchanged). The alternative — a single mutable row — would destroy the turn 1 plan as soon as turn 2 completes, making it impossible to diff the two plans or roll back. The storage overhead is negligible (one JSONB row per turn per trip).

36. **`turn` is added to `AgentRunRead` (the API schema) with `default=1` so the field is non-breaking for existing API consumers.** Any client that was consuming `/runs` before Phase 15 will now see `"turn": 1` on all rows — old rows get the default via the migration's `server_default="1"`. New rows written by Phase 15 carry the actual turn number. Clients that don't read `turn` are unaffected; clients that want to filter by turn use `?turn=N`.

## Phase 16 — User Preferences & Personalisation

37. **`user_preferences` is one row per user, keyed by `user_id` (PK + FK), lists as JSONB, and `GET` returns empty defaults instead of 404.** A surrogate `id` would need a separate unique constraint to enforce "one row per user" for no benefit. JSONB matches `trips.interests`; a `CHECK` constraint pins `travel_style` to `budget | mid-range | luxury` because both the PUT route and an LLM write it. `GET` returning `200` with empty fields means a new user and a user who cleared everything look the same to the frontend. `updated_at` uses SQLAlchemy `onupdate`, so no writer has to remember it.

38. **Preferences are injected once, into orchestrator *state*, in a node placed after intent parsing — not into each sub-agent.** The sub-agents' search nodes are structured pass-throughs with no system prompt, so "prompt injection" reduces to adjusting their structured input. Doing it at the three-plus call sites (initial flight search, replan loop, evaluator retry, refine, hotel/activities, retry) would scatter the logic; mutating state once makes every path inherit it, and `build_preference_updates()` is pure and idempotent so `/clarify` and refine (which re-enter with already-augmented state) are safe. The node must run **after** intent parsing because that node only fills `interests` when empty — injecting "vegetarian" first would stop it extracting the user's real interests from `raw_input`. Two rules keep injection conservative: `home_city` only becomes `origin` when no origin was given, and `travel_style` default interests (`budget → nature`, `luxury → wellness`) apply only when the trip has no explicit interests.

39. **The extractor is additive: lists are unioned, scalars are filled only when unset, and it never removes anything.** `PUT` is the full overwrite; the extractor must not be able to undo it. Because the table has no provenance column, "unset" is the only safe test for scalars — the cost is that an inferred `travel_style` never self-corrects until the user PUTs a new one (documented in `preference_extractor_v1.md`; fix is an `explicit_fields` column). Lists are capped at 20 items so repeated trips cannot grow them unbounded, and the cap never truncates existing items.

40. **`PreferenceExtractor` uses Claude Haiku 4.5 for free-text fields, keeps a deterministic fallback for `travel_style`, and validates every LLM output.** Dietary/airline/home-city statements are judgement calls on free text — a legitimate LLM use, unlike the Evaluator's checks (#21). `travel_style` is close to rule-based (stars + spend), so `infer_travel_style()` backs it up: LLM down, no `ANTHROPIC_API_KEY`, or unparseable reply → the trip still gets a style, and CI never makes a network call. The LLM output is coerced (enum, IATA regex, length caps) before it can touch the DB, which also bounds the damage from prompt injection via `raw_input`. It runs **after** `merge_node` so `planning_complete` is not delayed, and any failure is swallowed (with a `rollback()` so the shared session stays usable) — a preference-learning failure must never fail a trip. It does not run on targeted refinements: it is fill-only, so a refine would rarely change anything, and it saves an LLM call per refine.

41. **`preferred_airlines` is a soft ranking, not a filter, and is stored as 2-character IATA carrier codes.** Restricting the search to the preferred carriers would return zero flights whenever they don't serve the route, turning a preference into a hard failure and tripping the budget-decision escalate path. A stable sort moves preferred carriers first and drops nothing; `make_budget_decision` still uses the cheapest flight overall, so the preference never affects the budget branch. Codes (not names) are required because they are compared to the carrier code the flight provider returns; the PUT schema rejects anything else with 422. The new field had to be added to the MCP `FlightSearchInput` — otherwise Pydantic's default `extra="ignore"` would silently discard it and the wiring would look correct while doing nothing.

42. **`home_city` is resolved to an IATA code with the MCP server's own `_city_to_iata` table (lazy import), city table first, then 3-letter pass-through.** One source of truth beats a second copy of 40 cities. The city table goes first because some cities are valid 3-letter strings ("Goa" must map to `GOI`, not `GOA`). This imports a private helper across the backend/MCP boundary — accepted for now; follow-up is to move the table to a shared module. An unresolvable city leaves `origin` unset, so the existing `"DEL"` default still applies.


## Phase 17 — Frontend: Chat Interface & SSE Streaming

43. **Next.js `/api/*` rewrite proxies requests to FastAPI server-side; SSE connects directly via `NEXT_PUBLIC_API_URL`.** Browser fetch requests target `/api/...` on the same origin (`localhost:3000`), completely avoiding browser CORS complications in local dev. In production, changing `BACKEND_URL` redirects API calls without touching client-side code. SSE (`EventSource`) cannot be proxied through standard Next.js rewrites without buffering/connection termination issues, so it connects directly to the backend URL with the auth token passed via query parameter (`?token=`), which was already supported by `get_current_user_sse` (Phase 5).

44. **`useSSE` hook implements exponential backoff (1s → 30s cap) and preserves received event history across reconnects.** If the network drops or the connection drops during agent execution, resetting state would wipe the progress panel and show a blank screen. Retaining the event history ensures the UI always presents the latest known agent progress and status indicators while the hook silently attempts reconnection.

45. **Frontend planning state is governed by an explicit `PlanningPhase` state machine (`idle` → `planning` → `complete` / `clarifying` / `failed` → `refining`).** Rather than managing disparate boolean flags (`isPlanning`, `isRefining`, `isClarifying`), a single discrete phase drives the `ChatInput` placeholder, button states, and thread interactions. This prevents invalid UI states (such as submitting a refinement while a clarification prompt is active).

46. **`GET /trips/{id}/status` derives per-agent progress dynamically from `agent_runs` rows rather than adding state columns to `Trip`.** A single indexed query on `ix_agent_runs_trip_id` extracts the latest status of `flight_agent`, `hotel_agent`, and `activities_agent`. This provides an immediate polling fallback for clients where SSE is blocked or unsupported, without altering database schemas or introducing dual-state synchronization bugs. While a run is in flight only the rows written since the last closing `orchestrator` row count, so re-planning a finished trip starts again from 0/3 instead of showing the previous run as done.

## Phases 1–17 audit — end-to-end hardening (2026-10-02)

> Every item below was found by running the system for real (real Postgres, Redis, MCP subprocess, browser) rather than through mocks. Findings and evidence: `docs/phase1-17_audit.md`.

47. **Flights moved from Amadeus to Duffel.** Amadeus shut down its self-service portal on 2026-07-17, so neither flights nor hotels could ever return data. Flights now use Duffel's offer-request API over plain `httpx` (no SDK): the tool resolves city names to IATA codes itself (agents pass "Goa", not "GOI"), searches a round trip when `return_date` is given, sorts cheapest-first and treats `budget` as a hard cap. Duffel quotes in the account's billing currency with no currency parameter, so prices are converted with a small static FX table and offers in an unknown currency are skipped rather than mispriced — accepted as approximate until a rates source is added. Hotels followed in #64.

48. **A provider outage is a partial failure, not a budget conflict.** `make_budget_decision()` takes the flight error: only `NO_RESULTS` / `BUDGET_TOO_LOW` are about money and escalate. Anything else (not configured, API down, no airport for the destination) returns `continue` with `flight_cost=0`, so hotels and activities are still planned. Previously every flight failure produced "No flights found or zero budget" and a misleading `budget_conflict` — with a dead provider that failed 100% of trips. Sub-agent failures are also published on SSE (they were silent), and a sub-agent that would *ask* a question when run standalone is recorded as a failed search (`MISSING_INPUT`) instead of a successful empty one.

49. **The re-plan loop changes the search, not just a number.** The flight tool used to ignore `budget`, so re-planning returned the identical flights and always ended in escalate. Now attempt N lowers the cap (65% → 55%) *and* allows one more stop (`max_stops = 1 + N`, capped at 2), which is what can surface cheaper offers.

50. **The evaluator's budget check compares the draft to source prices, not to the user's budget.** `expected_total_cost()` recomputes the total the way `estimate_budget` does — cheapest flight + hotel nights at the *searched* price + activity costs — and `budget_mismatch` fires when the draft's `total_cost` is more than 5% off. The old code passed the trip budget as the expected total, so a ₹17,700 plan on a ₹50,000 budget was a "mismatch", retried three times and failed. Recomputing from the hotel search results (not the draft's own numbers) also catches a builder that misquotes a hotel.

51. **`log_agent_run` serialises writes per session.** One run shares one `AsyncSession`, and `hotel_activities_node` fans two agents out concurrently — two coroutines committing on one session is illegal in SQLAlchemy and crashed every real run at that node (unit tests mocked the DB). A per-session `asyncio.Lock` keeps the "one session per run" model (and its atomic `persist_node`) without giving each log call its own connection.

52. **The MCP client reads `structuredContent`, falling back to all text blocks.** FastMCP sends a list result as one text block per item; reading `content[0]` silently turned every list of flights/hotels/attractions into a single dict. The structured payload is exact (including the empty list), so it is preferred; the text fallback returns every block.

53. **Embeddings run as a spawned task with an in-flight counter.** `persist_node` used to await the OpenAI call, so `planning_complete` waited for it — about 7 s of retry back-off on every trip without an `OPENAI_API_KEY`. It is now fire-and-forget (`src/ai/utils/tasks.spawn` keeps a strong reference). `embeddings_pending` in Redis counts running jobs and `GET /admin/embedding-health` reports it next to the `pending_retry` backlog; the counter is reset at startup because no job survives a restart.

54. **One planning run per trip, and a trip can never stay "planning".** `/plan`, `/clarify`, `/replan` and `/refine` return 409 while a run is in flight (double submits used to start parallel orchestrators). The background task marks the trip failed and publishes `planning_failed` if the run crashes, and startup marks any trip still "planning" as failed — runs are in-process tasks, so none survives a restart. Trade-off: with several API instances a restart of one would fail runs owned by another; acceptable until Phase 27 moves runs to a queue.

55. **Refinements carry state forward turn over turn and actually change something.** The Redis planning state is saved only after a *successful* run and after refinements too (turn 3 used to refine turn 1's state). `full_replan` and `add_day` restart from the trip fields only, so retry and re-plan counters do not leak across turns; `full_replan` sets `intent_override` so "I'd rather go to Mumbai" really replaces the destination (fields were fill-only before), and a moved start date keeps the trip length. Targeted refinements pass the user's message to the builder as context — the search tools have no "closer to the beach" parameter, so without it the rebuilt itinerary was identical. `targeted_activities` re-extracts interests from the message; `targeted_flights` re-runs the budget check ("make it cheaper" policy) and escalates on conflict. A refinement that fails leaves the trip `completed`: the previous itinerary still stands. `persist_node` syncs destination / dates / budget back to the trip row.

56. **`POST /plan` asks instead of assuming, deterministically.** A trip row always has destination, dates and budget, so the only thing that can be missing is interests. With no interests and no free text to infer them from, `/plan` answers `200 {"status": "clarification_needed", "question": ...}` and starts nothing; `/clarify` runs the plan with the answer as `raw_input`. When free text is present and still yields no interests, the orchestrator assumes `["sightseeing"]` (the documented minimum in `orchestrator_v3.md`) rather than sending an empty list that ActivitiesAgent rejects. No LLM takes part in the decision (same rule as #6).

57. **Model IDs and keys are configuration.** `gemini-1.5-flash` was hard-coded in five places and has been retired; model IDs now come from `GEMINI_MODEL` / `GROQ_MODEL` (`src/ai/llm.py`), so the next retirement is an env change. The Gemini, Groq and OpenAI SDKs read their keys from `os.environ`, which pydantic-settings never populated, so keys in `.env` did not reach them — `config.py` now exports exactly those three. It deliberately does not `load_dotenv()` the whole file: that also switched on `LANGCHAIN_TRACING_V2`.

58. **The app starts from any directory.** `app/__init__.py` puts the repo root on `sys.path` (the agent layer lives beside `src/backend`), `.env` is located relative to the source tree rather than the working directory, and the MCP subprocess is started with `cwd` = repo root. The documented `cd src/backend && uvicorn app.main:app` failed on import before this. The Docker image now copies the whole `src/` tree (it lacked `src/ai`) and compose overrides `DATABASE_URL` / `REDIS_URL` with the service names.

59. **CORS: explicit origins from `CORS_ORIGINS`, no credentials.** Auth is a Bearer token (header, or `?token=` for EventSource) — there are no cookies, so credentialed CORS is unnecessary and `allow_origins=["*"]` with `allow_credentials=True` was both wider than needed and empty (`[]`) outside development. **Production policy:** set `CORS_ORIGINS` to the exact frontend origin(s) (e.g. the Vercel URL); never a wildcard.

60. **One error envelope, UTC timestamps.** Every error body carries `{"error": {"code", "message"}}` next to FastAPI's `detail` (kept so existing clients work); the frontend shows `error.message`. Datetimes are stored as naive UTC and were serialised without an offset, which browsers parse as local time — response schemas now use `UTCDateTime` and emit `…Z`. Provider error messages report the HTTP status only: `str(httpx.HTTPStatusError)` contains the request URL, API key included, and it was being stored in `agent_runs` and sent over SSE.

61. **Integration tests own a database and use the real migrations.** The fixture ran `create_all` / `drop_all` against the dev database, wiping it after every run while leaving `alembic_version` at head (so `alembic upgrade head` then did nothing). Integration runs now point at `<db>_test`, created on demand and migrated with Alembic — the production schema, cascades and HNSW index included — and tables are truncated between tests.

62. **The browser smoke test runs on a stub backend.** `tests/e2e/stub_backend.py` serves the real app (FastAPI, Postgres, Redis, LangGraph, SSE) with only the external APIs faked by `tests/fakes.network_stubs()` — the same stubs the integration test uses. A smoke test that needs five paid API keys does not get run; this one starts with `npx playwright test`. Start the real backend on :8000 first and the same spec exercises real keys.

63. **The trip page loads its state from the API and polls as a safety net.** It keeps the SSE stream open for the life of the page (pub/sub has no replay, so subscribing only after `POST /plan` raced the first events), loads the trip and latest itinerary on mount, and polls `GET /status` while a run is in flight so a missed `planning_complete` cannot hang the UI. SSE and polling both funnel into one `finishRun`, guarded so the outcome is handled once.

## First live run (2026-10-02) — providers and models that actually answer

> Everything in this section was decided against real API responses, with the user's keys.

64. **Hotels: LiteAPI (Nuitee), city name first, radius as the fallback.** Duffel Stays answered 403 ("not enabled for your account" — sales-gated), OpenTripMap lists properties but has no prices, Xotelo is RapidAPI-only. LiteAPI gives a free self-serve sandbox key and returns name, stars, review score, coordinates and a price in INR for the whole stay, so the tool needs no FX table and divides by nights. The search tries LiteAPI's own city match first because it is exact for cities; a region ("Kerala") matches none, so it falls back to a 25 km radius around the geocoded centre. Radius-first was rejected after it returned Chennai hotels for "Manali". Guests are put two to a room and the nightly price covers all rooms, matching how the orchestrator budgets (`remaining / nights` for the whole party). The `amadeus` dependency is gone.

65. **Geocoding: Nominatim instead of OpenTripMap's geoname.** OpenTripMap picks the most *populous* match — "Manali" became a Chennai suburb, so attractions and hotels were for the wrong place. Nominatim ranks by prominence and gets the hill station. It needs no key; results are cached for 30 days (its usage policy asks for caching and an identifying User-Agent). Searches are limited to India (`COUNTRY_CODE`), consistent with INR budgets and the Indian airport table.

66. **Attractions: one search per interest, 30 km radius, up to 10 results.** OpenTripMap returns results nearest-first, so one combined query filled up with whatever was closest to the centre — "beaches and history" in Goa returned only inland churches. Each interest now gets its own query and an equal share of the limit; plurals match ("beaches" → `beach`), unnamed places are dropped, and the radius reaches the coast from a region's centre. The orchestrator asks for 10 (the tool's maximum) so a week does not repeat the same five places.

67. **No OpenAI or Anthropic key: embeddings on Gemini, preference extraction on Groq.** The roadmap names OpenAI `text-embedding-3-small` and Claude Haiku 4.5. `gemini-embedding-001` is asked for 1536 dimensions — exactly the `embeddings.vector` column — so there is no migration, and the call goes through plain `httpx` with the key in a header (never in a URL that could be logged). The preference extractor reuses the builder's Groq model; the deterministic `travel_style` fallback is unchanged. Net effect: two LLM keys (Gemini, Groq) instead of four. Trade-off: vectors written by different embedding models are not comparable, so switching model later means re-embedding — the `embedding_model` column records which one wrote each row.

68. **Groq model is `openai/gpt-oss-120b`.** `llama-3.3-70b-versatile` answered 404 on the live account (retired). A builder call takes about 5 s and produced valid, in-scope JSON in every live run. Still a setting (`GROQ_MODEL`).

69. **"Explore the area" may repeat within a day; attractions may not repeat across days.** The first live runs showed both problems: five attractions recycled over five days, and — once the prompt forbade that — a day of three "Explore the area" slots rejected by the evaluator as `duplicate_activity`, failing the trip after three retries. The fallback phrase is free time, not an attraction, so the duplicate check now skips it. The builder prompt (v5) spreads attractions evenly, uses each once, keeps one hotel for the trip and charges N−1 nights for N days.

70. **`httpx` request logging is silenced in the MCP server.** `httpx` logs every request URL at INFO, and OpenTripMap / OpenWeatherMap take their key in the query string — the key was printed in the server log on every call.

71. **Refinement state is saved before `planning_complete` is published.** The route used to save the Redis planning state after the orchestrator returned — but the graph publishes `planning_complete` and then still runs preference extraction (an LLM call), so for a few seconds a client that had been told "complete" got `409 No prior planning state` on `/refine`. Found in the first live browser run; the stub backend finishes too fast to show it. `merge_node` now awaits an `on_complete(state)` hook (passed in by the route, like `publish_fn`) just before publishing. Delaying the event until the run returned was rejected: it would put the extractor's latency back in front of the user (#40).

72. **Token limits are sized for a reasoning model.** `openai/gpt-oss-120b` spends completion tokens reasoning before it answers. The preference extractor's `max_tokens=300` (sized for Claude) left nothing for the JSON on a full-size trip — an empty reply, silently replaced by the heuristic, so "we are vegetarian" was never learned. Now 2048; the builder's limit went from 4096 to 8192 so a long trip cannot be truncated mid-JSON.

73. **A sentence typed into the destination field is parsed, not searched for.** The first hands-on run put "Relaxed trip from Delhi, to Ayodhya and history" in the form's Destination field; every tool then looked for a place with that name and the trip failed with three unhelpful errors. A destination of more than three words is now treated as free text: it goes through intent extraction together with the chat message, and the place found replaces it (other form fields still win). The corrected destination is written back to the trip even when the run fails. A word-count check is crude but costs nothing for normal names and at worst one extra LLM call for a long place name.

74. **"Increase budget" raises the budget to what the flights need, not by a fixed 25%.** With ₹18,234 of flights on a ₹20,000 budget, +25% is still a conflict, so all three offered options were dead ends. `viable_budget(flight_cost)` is the smallest budget (rounded up to ₹500) that passes the check outright; the option shows that figure and `POST /replan` applies `max(+25%, viable)` using the last `budget_decision` row.

## Phase 18 — Map View

75. **Coordinates are attached to the itinerary by code, from the search results — the prompt rule is a courtesy.** The roadmap says "update the prompt to always include lat/lng". The prompt does ask (v6), but `_attach_source_data()` then overwrites each slot's coordinates by looking the activity up by name in the attractions the tools returned. Names have already passed the data-scope check, so the lookup is exact; a model copying long floats is not, and a wrong coordinate fails silently as a misplaced pin. The same step attaches category, rating, hotel details and the outbound flight, so the frontend needs no second request and no geocoding.

76. **An attraction without coordinates is dropped at the tool; a missing coordinate later is a warning, never a failure.** Dropping at the source is what makes "always populated" true rather than hoped for. In the save path `persist_node` logs any real activity it cannot pin and records it on its `agent_runs` row (`unmapped_activities`) so it can become a metric. "Explore the area" is free time, not a place — it is neither pinned nor counted as missing, otherwise the 95% target would measure how much free time a trip has.

77. **The outbound flight shown is the cheapest one, set on day 1.** The builder never chose a flight (`"flight": null`), yet its cost math assumed the cheapest. Attaching that same flight makes the itinerary say what it charges for, and gives the map its two airport markers from Duffel's own airport coordinates — no airport table to maintain.

78. **Leaflet with `divIcon` pins, loaded client-only; the map frames the destination, not the journey.** `react-leaflet` 4 is the React 18 line (5 needs React 19). Leaflet touches `window` on import, so the component is loaded with `next/dynamic` and `ssr: false`. Pins are small HTML marks: no marker images to bundle (the classic broken-icon problem) and the stop number fits inside (#82). The view fits activities, hotel and arrival airport; the departure airport is drawn but excluded from the bounds, because framing Delhi and Goa together makes every pin overlap. Map data is built by a pure function (`lib/map.ts`) so the rules — what is a pin, what is a route, what is unmapped — are in one place, away from Leaflet.

79. **Free time is said once per day.** The builder filled every spare slot with "Explore the area", so a day with one booked activity read as two more "activities" and a free day repeated the phrase three times. `_normalise_free_time()` runs before validation: a day with a real activity drops its free-time slots (an empty slot is just empty), and a day with none keeps exactly one, in the morning, which the UI shows as "All day · Free time". The frontend collapses repeats too, so itineraries saved before this still read correctly. The phrase and the slot names live in one module (`src/ai/itinerary.py`) instead of five copies.

80. **The draft's shape is validated before anything reads it.** `build_itinerary` used to walk the parsed JSON (data scope, budget math) and only then build the pydantic model, so a slot that was a string or a `days` that was a dict raised `TypeError` deep in a helper — a crash, not a retry. It now builds `ItineraryDraft` first and reports `SCHEMA_INVALID` like any other builder failure. A `null` cost is read as 0: the model writes it for free places, and rejecting it failed otherwise good drafts.

81. **Day colours are a validated palette, and shape takes over when the colours run out.** The first palette was picked by eye; blue and purple turned out to be ΔE 1.3 apart under deuteranopia — the same colour. On a map any two days can sit next to each other, so the seven colours (`#2a78d6 #1baf7a #882255 #ee7733 #117733 #56b4e9 #4a3aa7`) were chosen by search and checked for **every pair**: colour-blind ΔE ≥ 9.0, normal-vision ΔE ≥ 16.3. A day's colour belongs to the day number, never to its position in a filtered view. Past day 7 the colours repeat with a different pin shape (circle → square → diamond), giving 21 distinct marks; a generated eighth hue would have broken the guarantee. The hotel is gold `#f4c430` and always a square with a bed icon, so it is never told apart from orange by colour alone.

82. **A pin's number is its place in the day, and the same pin appears in the day card.** The roadmap's sketch numbered pins by day, which the colour already says. Numbering by visiting order (1 → 2 → 3) lets the map be read as a route without following the line, and the day card shows the identical mark next to each stop — clicking it scrolls to the map and opens that pin. The legend is always visible and its day entries are filters; text is never coloured, only the mark beside it.

83. **Category comes from the most specific OpenTripMap kind; rating is the source's popularity rate, never invented.** A place carries many kinds ("natural,nature_reserves,interesting_places"), and taking the first kind the lookup table happened to recognise labelled a wildlife sanctuary and a zoo "history". The map is now an ordered list, most specific first. `rate` is 1–3, or 5–7 for the same scale on a heritage site (observed: 2, 3, 6, 7) — not a five-star score — so the UI shows "Worth a stop / Popular / Top attraction" plus "Heritage site", and an unrated place shows nothing (the tool used to default it to 3.0). Because both fields changed meaning, the attractions cache key gained a version (`attractions:v2`): entries cached before would otherwise have been served as current for six hours.

84. **Map tiles are OpenStreetMap's, toned down in CSS.** CARTO's lighter basemap looked better and now answers "API key required" without an account. OSM's standard tiles need no key; a CSS filter on the tile pane (lower saturation and contrast) keeps them from competing with the pins. The URL and attribution are settings (`NEXT_PUBLIC_MAP_TILE_URL`, `NEXT_PUBLIC_MAP_ATTRIBUTION`) because OSM's tile policy rules out heavy production use — a hosted provider is a config change, not a code change.

85. **A budget conflict's options are stored and returned by `GET /status`.** The three ways out were only ever sent in an SSE event; pub/sub has no replay, so reloading the page left "Needs attention" and nothing to click. `escalate_node` now writes the reason and the options to its `agent_runs` row (it used to store a count) and `/status` returns them as `budget_conflict` while the trip is failed and that run is still the latest. No new table or column: same reasoning as #46. A conflict from a row written before this change has a reason and no options, and the page says "describe a different trip" instead of showing an empty grid.

86. **A refinement interrupted by a restart goes back to "completed".** #54 marked every trip still "planning" at startup as failed. For a refinement that is wrong: the previous itinerary still stands (#55), yet the trip showed "Needs attention". Recovery now sets such a trip to completed when it has an itinerary and failed otherwise.

87. **Playwright runs on its own stack.** The stub backend used port 8000 and the dev database, so the browser tests could not run while the dev servers were up, and a run against a real backend left test trips in real data. The tests now start a stub backend on :8100 with its own `<db>_e2e` database (emptied at start) and a second Next.js dev server on :3100 with its own build directory (`NEXT_DIST_DIR=.next-e2e`). This replaces the last sentence of #62: the spec asserts the stub's data ("Fort Aguada", "Found 1 flight"), so it is not meant to be pointed at real keys — the live check is done by hand (HOW_TO_RUN, Step 16).

88. **The progress panel knows what a refinement repeats.** `GET /status` counts only the run in flight (#46), and a targeted refinement runs one search, so after "switch the hotel" the panel showed flights and activities as "not started" beside "Planning complete". The page now records, per run, which searches are carried forward — `POST /refine` already returns the refinement type — and shows those as done with what they found; when a run ends it re-reads `/status`, which by then counts every search behind the plan. The panel is hidden until there is something to report: three idle rows on an unplanned trip said nothing.

89. **One small design system, no component library.** Tokens (warm neutrals, three status colours, one decorative gradient) live in `tailwind.config.ts`; a few component classes (`.btn`, `.card`, `.input`, `.chip`, `.pin`) in `globals.css`; icons from `lucide-react`; type is Inter with Fraunces for headings via `next/font`. shadcn/ui was considered and left out: the app has only a handful of controls (button, input, card, chip, badge), and a copied-in component set is more code to own than those. Rules that hold everywhere: status is an icon plus words, never colour alone; one large figure per view (the trip total); a running refinement dims the current plan instead of replacing it with a skeleton. On a small screen the plan comes first and the assistant after it, with a floating button back to the composer — a composer pinned over the content hid the map controls and the last day card.

## First run of a trip the planner cannot serve (2026-10-02) — "London", 365 nights

> Found by a hands-on test: the trip was saved as "planned" with a one-day itinerary of parks in Pune, and asking for a change answered "HTTP 500". Five separate causes.

90. **Short LLM calls make one attempt and have a second provider.** Gemini's free tier allows 20 requests a day per model. Once it ran out, every call spent ~36 s in the SDK's default retries before failing: each plan lost half a minute to intent parsing (and then ignored the user's text), and `POST /refine` — which awaits the classifier — outlived the frontend proxy's 30 s, so the browser saw "HTTP 500" while the backend carried on and saved a new itinerary nobody was shown. `src/ai/llm.ask()` is now the one way to send a short prompt: Gemini with `max_retries=1` and a 15 s timeout, then Groq's small model (`GROQ_SMALL_MODEL`, `openai/gpt-oss-20b`), which has its own rate limits and answered the intent prompt in 0.4 s. A daily quota is not something a retry inside a request can wait out. The five call sites that built their own Gemini client now share this.

91. **A destination is a place you can travel to, and one abroad is reported as abroad.** The place search is limited to India (#65); inside India "London" matches "The London Bridge", a road in Pune, and the geocoder took the first match of any kind. It now accepts settlements and regions (then natural features), never a road or a shop. When the in-country match is missing or minor (Nominatim importance below 0.3), the whole world is searched: a clearly better-known namesake abroad — London, or Bali against a town in Rajasthan — makes the tool answer `OUTSIDE_COVERAGE` ("London is in United Kingdom. This planner covers trips within India for now."). A well-known Indian place still costs one request. Results, including "abroad" and "unknown", are cached under a new key (`geocode:v2`) so the wrong coordinates cached for "london" are not served for another 30 days. Supporting destinations abroad is a separate decision: it needs airport lookup beyond the Indian table and a country for the hotel search.

92. **A run that finds nothing fails, and says why.** With no flights, no hotel and no attractions the graph used to go on to the builder — which, given the Pune attractions, produced a plan, and given nothing would have retried three times before failing with "no source data". `route_after_search` now sends such a run to `nothing_found_node`: the trip is failed, the reason is the destination error when there is one, and it is published and stored. `GET /status` returns it as `failure_reason` (alongside `budget_conflict`, #85) so a reloaded page can still say why; a failed build's reason comes back the same way.

93. **The evaluator checks that every day of the trip is planned.** A fifth check, `missing_days`: each date from start to end has exactly one entry. The builder's prompt (v7) now states the number of days rather than leaving the model to count, and the test stub writes one entry per day like the real model does. Counting nights for the travel-style heuristic was off by one for the same reason (it counted days) and now counts hotel nights.

94. **A trip is at most 14 nights.** The searches return at most ten attractions and the builder writes the whole plan in one reply, so a longer trip is mostly empty days — and a year-long one cannot be written at all. `TripCreate` rejects it with a clear message and the form limits the end date. A refinement can still extend a trip a day at a time; the coverage check (#93) is what guards the result.

95. **The page keeps listening when the request that starts a run fails on the way back.** If `POST /plan` or `/refine` errors (a proxy timeout), the page now asks `GET /status` before giving up: when the trip is "planning", it waits for the outcome as usual instead of telling the user something went wrong while a run is in flight.

96. **The MCP SDK is pinned below 2.0.** `requirements.txt` allowed any version; CI and every fresh install picked up 2.x, which renames the result fields the client reads (`isError` → `is_error`, `structuredContent` → `structured_content`), so every tool result would have been unparseable. The app is built and verified on 1.x.

## The assistant says what changed (2026-10-02)

97. **After a change request the assistant lists what changed — worked out by comparing the two plans, not by a model.** The reply used to be "Done — the plan now comes to ₹X". The page holds the itinerary from before the request and the one that came back; `lib/changes.ts` compares them and reports the stay, the flight, places added / removed / moved, the trip's length and dates, the destination, and how the total moved ("Stay: Umaid Mahal → Radisson Blu (₹8,014 → ₹11,766 a night)"). A model writing this summary could claim a change that did not happen; a diff cannot. When nothing a traveller would notice is different, the assistant says the plan came out the same. It is done in the frontend because both plans are already there on either path a run can end (SSE or polling) — no new endpoint, no stored text to keep in step.

98. **A targeted refinement changes only what was asked for.** The summary (#97) showed what #55 had missed: the builder rewrites the whole plan each time and had never seen the previous one, so a new hotel came with every stop reshuffled, different activities swapped the hotel back, and "add a food stop" removed every stop that was not food. Now the builder is shown the current plan and told to keep the rest (prompt v8); the lists it chooses from are narrowed to what the plan already uses for everything the request is not about; newly found places are added to the plan's places instead of replacing them.

99. **A flights refinement keeps the flights already found in the running.** The plan always carries the cheapest flight, and prices move between searches (a re-search for "make it cheaper" came back ₹169 dearer). With the earlier flights still on the list the cheapest can only stay or improve; when nothing cheaper turns up, the assistant says the plan is unchanged. Consequence: such a refinement can no longer end in a budget conflict unless the plan had no flights before.

## Phase 19 — PDF Export

> Build log: `docs/phase19_build_log.md`. The numbers in this section were measured on the machine it was built on.

100. **The PDF is built with ReportLab, not WeasyPrint.** The roadmap leaves the choice open. WeasyPrint lays out HTML and CSS, so the PDF could have shared the page's markup — but it draws through Pango and GObject, system libraries that `pip` cannot install. On the laptop this was built on (no Homebrew) WeasyPrint 70 installed and then failed on import: `OSError: cannot load library 'libgobject-2.0-0'`. Using it would have meant a machine-level prerequisite for every developer, an `apt-get` step in CI and in the Docker image, and unit tests that mock the renderer. ReportLab 5 is one pure-Python wheel: the unit tests build the real PDF and read it back with `pypdf`, and the same suite passes in a bare `python:3.11-slim` container with no Pango, GObject or Cairo in it. The price is that the layout is code (`app/pdf/document.py`, `flowables.py`) rather than a stylesheet.

101. **The static map is drawn from map tiles, not fetched from the Google Maps Static API.** The roadmap names Google's API. It needs a key on a billing account, and this project runs on free tiers with no card (Google Maps was swapped for OpenTripMap for that reason early on). `app/pdf/static_map.py` fetches the tiles of one view — 20 at most — stitches them with Pillow, tones them down the way the web map's CSS filter does, and draws the pins itself. That last part is what a static-map API could not have given: the pins are the web map's own (#81, #82) — the day's colour and shape, the stop's number, the hotel in gold. The tile server is a setting (`MAP_TILE_URL`, for the reason in #84). The default is OpenStreetMap's, used as its tile usage policy asks: a User-Agent that names the app, tiles kept seven days (in Redis), only the tiles of the view being drawn, the attribution on the picture. The web map's default URL lost its `{s}` subdomain while reading that policy: it names one URL.

102. **A map that cannot be drawn is left out, and the answer says so.** Roadmap: omit the image, log a warning, the PDF still downloads. Every failure — a tile that will not download, a body that is not an image, tiles slower than 12 s in all — becomes one `StaticMapError`; `export_itinerary` logs it and builds the PDF without the map page. The response carries `X-Itinerary-Map: included | unavailable | none`, and on "unavailable" the page tells the user that downloading again may bring the map; a PDF that silently lacks a page looks like a bug. The error text never contains the tile URL — a hosted provider's key lives in it (#60, #70).

103. **The PDF reads an itinerary by the trip page's rules, and as forgivingly.** `app/pdf/plan.py` re-implements what `lib/map.ts`, `ItineraryView` and `CostSummary` do — which stops are shown, the number on a pin, how the total splits, when a budget is "tight" — so paper and screen agree; tests read the day palette and the category labels out of the TypeScript source, so the two cannot drift apart unnoticed. It does not validate against the builder's schema: an itinerary saved before the flight or the coordinates were attached, or with free time repeated in every slot, is shown by the page and must export too. One thing the PDF adds: a ledger has to add up, and the builder's total may be ₹500 away from its parts, so the difference gets a line of its own ("Other").

104. **Pins that would hide each other are nudged apart.** The first real itinerary exported (Kedarnath) has the hotel and the first two days' stops within a hundred metres: on a still picture one pin covered the other two. `spread()` pushes any two pins closer than 0.85 of a pin apart along the line between them, by as little as it takes; pins on the very same spot fan out in an order that depends only on their place in the list, so the same plan always draws the same map. The web map needs none of this — there you zoom in.

105. **Inter and Fraunces are bundled, as static subsets.** ReportLab's built-in fonts have no ₹, and the PDF should look like the page it came from. The upstream files are variable fonts, which ReportLab cannot use: it draws the default instance, for Fraunces "9pt Black". `fonts/build_fonts.py` pins each face to one instance and keeps Latin, punctuation, ₹ and arrows — four files, 232 KB, the same bytes on every rebuild, with their OFL texts beside them. Text in another script (Devanagari) prints as empty boxes and the PDF is still built; real support belongs to the multi-language phase.

106. **One PDF is laid out at a time, off the event loop.** `build_pdf` runs in a worker thread — laying pages out on the loop would stall every open SSE stream — and takes a lock: every document shares the registered fonts, and ReportLab's subsetting of them is not re-entrant. Without the lock, 40 of 96 concurrent builds failed inside `makeSubset`. A build takes about 100 ms (two passes: "Page 2 of 5" needs the 5), so taking turns costs nothing that matters. The map picture antialiases each pin and each route on a small picture of its own; one full-size oversampled layer looked the same and took 85 MB more for every map.

107. **The export is sent whole, named in ASCII, and never cached.** The roadmap says "streams PDF". The file is a few hundred KB built in memory, and its page count has to be known before the first byte is right; it is sent with `Content-Length`, so the browser can show progress and notice a download that was cut off. `Content-Disposition: attachment; filename="trip-goa-2027-12-10.pdf"` — the date is the trip's first day, and the name is reduced to ASCII so it is valid in a header on any client (a destination with no ASCII letters leaves `trip-<date>.pdf`). `Cache-Control: private, no-store`, because the next refinement changes the document. The database connection is released before the map is fetched, and Redis is optional here (`get_redis_or_none`): it is only the tile cache.

108. **The button fetches the file and hands it to the browser; a failure is a toast.** The token travels in a header, which a plain link cannot send. `?token=` in the URL would work — the SSE stream authenticates that way, having no choice — but it puts the token in the browser history and in logs, so the page does fetch → blob → a temporary link. The toast is one small component of our own (#89): one at a time, gone after seven seconds, `role="alert"` for a failure and `role="status"` for a note, rendered into `<body>` so the dimmed plan does not dim it, and placed under the header because the bottom of a phone screen has the "Ask for a change" button.

109. **The stub stack answers for a tile server of its own.** The integration tests and the Playwright stack share Redis with the dev servers. Their first runs cached blank test tiles under the real tile server's keys — a real export of Goa would have been drawn on them for a week. The cache key carries a hash of the tile URL, and `network_stubs()` now sets a URL of its own (`STUB_TILE_URL`); an integration test asserts the keys are never the real server's.

110. **Playwright finds the project's Python itself.** The documented fallback, `PYTHON=../../.venv/bin/python npx playwright test`, never worked: the stub backend is started from the repo root, so the path was looked up two levels above the repo. The config now resolves a relative `PYTHON` from the frontend directory and, when none is given, uses the repo's `.venv` — `npx playwright test` works whether or not the venv is active.

111. **`npm run lint` works: ESLint with `next/core-web-vitals`, and nothing else.** Phase 18 left the script asking to be set up. The stock Next.js rule set — the React hooks rules and the Core Web Vitals checks — found nothing to change in the code as it stood, so no rule is switched off and there is no configuration of our own to maintain. It is not in CI yet: the frontend's type check, lint and browser tests are run by hand until the CI phase (28).

## Phase 20 — Frontend Polish

> Build log: `docs/phase20_build_log.md`. The numbers in this section were measured on the machine it was built on.

112. **The itinerary is streamed while it is written, a few tokens at a time.** `ItineraryBuilder` asks Groq with `astream` and hands each piece to `_TokenStream`, which publishes `builder_token` events `{"token", "seq"}` on the trip's channel. gpt-oss-120b writes about 450 tokens a second, so one Redis publish and one SSE message per token would be hundreds a second per trip: the pieces are joined and sent every 50 ms (the first one at once — it tells the page writing has begun). On the live model a three-day plan came as 27 events over 1.4 s. `seq` counts from 0 within one build; the text only makes sense from its start, so a page that joins late or misses an event waits for the next build. What is streamed is the model's unchecked reply: the itinerary that is saved is still the one parsed, validated and passed by the evaluator afterwards, and a reply that fails those checks is never saved — the build is retried and streams again from 0.

113. **The live preview reads the JSON as it arrives — not a markdown preview.** The roadmap asks for "a live markdown preview", but the builder writes JSON — its validated shape is what makes the plan checkable (#24, #80). Shown raw it is braces and quotes. `lib/draft.ts` reads a JSON text that is not finished — an object not yet closed, a string cut off mid-word — and `LiveDraft` shows the days and the places named so far, with a caret where the next word lands. Pure functions, tested in the browser like the change summary (16 cases, `e2e/draft.spec.ts`).

114. **A change request moves only the part it changes, and marks only what came back different.** A targeted refinement or a retry works on one section — flights, stay or activities (`SECTION_OF_REFINEMENT`); while it runs, only that section's rows and cost tile pulse with "Updating…" and the rest of the plan stays still. A full re-plan marks the whole plan. When the new plan arrives, `changedParts()` compares the two plans part by part and tints what differs green, labelled "Updated", for five seconds. Like the change summary (#97) it is a comparison, not a claim: nothing is marked that did not change. Both states have words, so neither depends on motion or colour; with reduced motion they are still pictures. The composer above a finished plan is labelled "Refine this trip:" (roadmap) rather than pre-filled with it — a pre-filled prefix would have to be deleted before every message.

115. **A failed search can be run again on its own: `POST /trips/{id}/retry`.** A plan is built from whatever the searches found (#48), so a provider that was down leaves a plan without flights, a stay or things to do. The progress panel says which search failed and why, and offers a Retry beside it. `{"agent": "hotel_agent"}` repeats that one search as the same targeted pass a refinement makes (#98), with a fixed request in place of the traveller's ("A place to stay has now been found: add it to the plan…"): no model decides what to do, the request is not re-read, and the plan keeps everything else. If the search fails again, the run ends `planning_failed` naming it and nothing is rebuilt. A run that failed outright has no plan to keep, so its Retry plans the whole trip again from the trip's fields and what the traveller last wrote — or asks for interests, as `/plan` does, when they wrote nothing. A targeted retry needs the last run's state; once Redis has expired it the answer is 409 "This plan is too old to retry a single search".

116. **A failure is told in the traveller's words, and Retry is offered only where it can help.** Found on a live run: a destination typed in Devanagari is under no airport, and the panel showed the tool's own words — "Pass an IATA code or add the city to _CITY_IATA in tools.py" — beside a Retry that could only fail the same way. `src/ai/utils/failures.py` words each tool error code for a traveller ("This search is not set up on this server", "The flight provider did not answer"), keeping the tool's message where it already reads well ("No hotels within ₹4,000/night in Goa."), and says whether a second try can change anything: a provider that errored or timed out may answer; an unknown destination, nothing within budget or a date in the past will not. Both reach the page — in the live event and in `/status` (`progress.retryable`) — and the panel leaves the Retry out where it cannot help. A run that failed outright keeps its Retry: what failed there can be anything.

117. **A page loaded in the middle of a run knows what the run is.** The `planning_started` event says whether a run is a refinement and which section it touches; a page that loads after it has gone by (a reload, a second tab) only has `GET /status`. The route notes the run in Redis while it is in flight (`trip:{id}:current_run`, one hour, cleared in a `finally` however the run ends) and `/status` returns it as `run`. For a targeted run, `/status` now reports the two searches it does not repeat as they last ended instead of "pending" — Phase 18's known limit, where a page loaded mid-refinement showed all three searches running.

118. **On a phone, the planning progress is a bottom sheet.** Below the `lg` breakpoint the assistant column sits under the plan, so its progress is out of sight exactly while it matters. There the panel lives in a sheet pinned to the foot of the screen: one line ("Searching — 1 of 3 done", "The hotel search failed") that opens to the full panel. It is rendered in one place or the other (`useWideScreen`), never both, so its buttons exist once — for screen readers and for tests. The "Ask for a change" button stacks above the sheet in the same fixed container and hides while the sheet is open: in the first version it covered the sheet's Retry, which the 375 px test found.

119. **Every view is checked at 375 px in the browser.** One Playwright test walks the sign-in page, the trips list, a trip being planned, a plan with a failed search, a run that failed and a budget conflict at 375 × 812, and asserts for each that nothing is wider than the screen. The budget conflict's options were already tappable cards (Phase 10/17); Phase 20 kept them and put them under the same test.

120. **The stub backend fails on purpose, by destination.** The browser tests need searches that fail and then answer: Hampi / Badami — the hotel search is down until it is retried; Shimla / Manali — every search is down until the trip is retried; Kaza — no airport is known for it, every time; anywhere else, a second hotel search finds a different hotel, so a refinement visibly changes the plan. "Down, then fine" goes by how often the same search has been made (odd: down, even: answers), so a stub server left running behaves the same on the next run. The stand-in model pauses 15 ms between pieces of its reply, or it would be done before a browser could draw anything.

### The PDF in the scripts of India

121. **Text in the scripts of India is drawn in Noto, shaped by HarfBuzz.** Phase 19's fonts were Latin only (#105): a destination typed in Devanagari printed as empty boxes. A font alone is not enough — Devanagari, Bengali, Tamil and the rest join consonants into conjuncts and move vowel signs, Urdu joins its letters, and ReportLab does that only through `uharfbuzz` (`reportlab[shaping]`). It shapes one word at a time, in the font of the word's first piece of text, so `app/pdf/scripts.py` picks one font per word: the main font if it can draw the whole word, otherwise the Noto font of the word's letters, which also carries ASCII and common punctuation so that "(केदारनाथ)" or "श्री-Krishna" stays one word. Only those words are tagged, and only a paragraph that has one is shaped: a plan in Latin comes out as before (the same four faces embedded; build time 20 ms against 19). The output was compared with Chromium's for every script.

122. **Thirteen families: the scripts of India's scheduled languages, and Tibetan.** Noto Sans for Devanagari, Bengali, Gurmukhi, Gujarati, Odia, Tamil, Telugu, Kannada, Malayalam, Arabic (Urdu, Kashmiri, Sindhi), Ol Chiki and Meetei Mayek; Noto Serif Tibetan — there is no Noto Sans Tibetan — because OpenTripMap names many monasteries in Ladakh and Sikkim in it. Each in Regular (body text) and Medium (everything set in Inter Medium or SemiBold, and the Fraunces headings), built by `fonts/build_fonts.py` from pinned upstream files like Inter and Fraunces, keeping every layout feature. 3.6 MB in the repository, Tibetan 1.3 MB of it; a PDF embeds only the glyphs it uses. Inter now carries Greek and Cyrillic too (80 KB a face instead of about 57). Scripts outside India's — Chinese, Thai — still print as boxes; the planner serves trips within India.

123. **Right-to-left words are reversed line by line, when the paragraph is drawn.** ReportLab's own right-to-left support needs `rlbidi`, which is not on PyPI. HarfBuzz lays out the letters of an Urdu word right to left; the order of the words is ours. As a browser does, the lines are broken in reading order — so the first words are on the first line — and then each line is drawn with its stretch of right-to-left words, numbers between them included, reversed (`ScriptParagraph`). A number keeps its own direction: "گلی 12 لال چوک" does not become "21". Doing it at drawing time leaves the layout as ReportLab made it, so a paragraph split across two pages is unaffected. Verified by watching ReportLab's line drawing and mapping each drawn word back to its place in the text; reading the order off a picture of Arabic is not reliable. Lines keep the paragraph's leading: Noto Arabic and Tibetan declare line heights of 21 and 28 pt at 10 pt, and sizing lines by them would open gaps a browser with a fixed line height does not.

124. **Names are cut between syllables, and the file is named in the destination's script.** The PDF shortens long names so a card can never outgrow a page (#103); cut between a consonant and its vowel sign and the sign is drawn on a dotted circle. `formatting.clip()` steps back to the start of the syllable. The download is now `attachment; filename="trip-2027-12-10.pdf"; filename*=UTF-8''trip-%E0%A4%97…` — RFC 6266's `filename*` names it "trip-गोवा-2027-12-10.pdf" and the page reads it first; the ASCII `filename` stays for clients that cannot (#107). Letters, marks and digits of any script are kept, everything else becomes a hyphen.

## Phase 21 — Smarter Budget Intelligence

> Build log: `docs/phase21_build_log.md`. The numbers in this section were measured on the machine it was built on.

125. **Seasons are a table of multipliers by kind of destination.** `src/ai/pricing.py` holds five profiles — coast, heritage, hills, the high Himalaya, and India-wide holidays for everywhere else — each twelve monthly multipliers against the destination's cheapest month, and about ninety destinations matched to one by a whole word of their name ("North Goa" is coast). Goa in December is 1.4× Goa in July, the roadmap's figure. A month is peak at 1.25 and above, off-peak at the profile's lowest, shoulder in between, and the range a price may move before it is booked is ±20%, ±15% or ±10% accordingly. The figures are approximations, in one table so they can be tuned; the Char Dham sit with the Himalaya because they are shut in winter, not crowded in December. A destination typed in another script matches no name and follows India-wide seasons.

126. **`estimate_budget` takes prices as they are for the month; the season sets the range and the off-season price.** The roadmap asks the tool to take the destination and the month. A fare found for December dates already carries December, and scaling it again would count the season twice — so the tool scales nothing. It reports the season and its multiplier, the range the total will likely land in once booked (`total_min`, `total_max`), and what the same trip costs in the off-season (`off_peak_total`). `nights` is optional and defaults to `days`, the tool's Phase 3 contract. The roadmap's example, `estimate_budget(8000, 3000, 5, 2000, "Goa", 12)`, gives ₹33,000, likely ₹26,400–₹39,600, peak season, ₹23,571 in the monsoon. The arithmetic is in `pricing.py` and shared by the MCP tool, the budget check and the evaluator, so nothing in the pipeline makes an MCP call to price anything.

127. **The evaluator's tolerance is the estimate's range, and a misquoted hotel is caught exactly.** Roadmap: the itinerary's total must fall within `[total_min, total_max]`. The total is recomputed from the source prices — the cheapest flight, each hotel night at the searched price, the activities as drafted — and the range around it is the season's ±10–20% instead of a flat 5%. A band that wide would let a misquoted hotel price through, and the 5% check was what caught one (#24) — so the evaluator now also compares each hotel's price in the plan with the search's, within ₹50 or 1%. That is stricter than before, and does not depend on how big the trip is: 5% of a ₹2,00,000 trip let a ₹10,000 misquote pass. A caller that passes no range gets the 5% as before.

128. **A budget conflict prices the trip as asked and three ways out — with arithmetic, not searches.** Phase 10's rule still decides when to stop (flights above 65% of the budget). When it does, `src/ai/agents/budget_alternatives.py` prices the trip as asked — the real fare, a typical 4-star stay and things to do, in that season — with its range, and then:

    - a cheaper stay: a 3-star hotel, or a budget one when only that fits;
    - a shorter trip: the longest one that fits, just as comfortable;
    - the off-season: the same trip in the nearest off-peak month at least 30 days away, the fare moved by the two months' multipliers.

    Every amount is in whole rupees, rounded to ₹100 and said as "about"; whether it fits is said in words. Nothing is searched for any of it — a test asserts that no agent and no tool is called. The roadmap's scenario (Goa, five days, ₹40,000, ₹28,000 of flights) gives: a budget hotel ₹38,200, which fits; 2 days ₹35,700, which fits; June, with flights about ₹8,000 less (the roadmap's figure), ₹40,500 — ₹500 over. The typical costs are India-wide off-season figures: a room for two at ₹1,200, ₹2,500, ₹4,500 or ₹9,000 a night by kind of hotel, and ₹500 a person a day for things to do (#19's figure).

129. **The ways out travel in the `budget_conflict` event, not a separate `budget_alternatives` event.** The roadmap names `{"event": "budget_alternatives", "options": [...]}`. The conflict and its options arrive as one event — with the priced trip they are measured against (`estimate`) — so a page never holds a conflict without its options, or options without the conflict they answer. The acceptance — "the budget conflict SSE event includes 3 alternatives with concrete amounts" — holds as written. `GET /status` hands back the same (`budget_conflict.estimate`) after a reload.

130. **A trip that fits at typical prices is not stopped.** The flight-share rule is blunt: two days in Goa can spend 70% of the budget on flights and still fit. When the rule would stop a trip, but the trip as asked — a 4-star stay and things to do — fits the budget at typical prices, the check goes ahead and says why: "but at typical prices the rest still fits: … about ₹35,700 of ₹40,000". Without a fare there is nothing to price, and the trip stops as before. The integration scenario's fare went from ₹28,000 to ₹30,000: at ₹28,000 the trip comes to exactly ₹40,000 at off-season prices, and the test would have passed or failed with the month it ran in.

131. **A way out the traveller picks is gone ahead with — no more dead ends.** Before, "Shorten the trip by 2 days" re-planned on the same flights, and the check, which does not look at a trip's length, stopped the traveller again, every time: a dead end, like the +25% budget of #74. Now `POST /replan` applies the option as the conflict offered it, read back from the stored conflict: the length, the dates, the budget. A shorter trip or a cheaper stay leaves the flights as they are, so the check goes ahead with it instead of asking again ("going ahead with the shorter trip you chose"); the choice stays in the run's state, so a later refinement does not stop the trip either. The off-season brings new flights, and they meet the check as usual. A choice the conflict did not offer is refused (409), and so are off-season dates that have passed. "Search connecting flights" is no longer offered after a re-plan has searched them. The made-up savings of Phase 10 — "₹flights × 0.35", "~₹8,000–15,000" — are gone; the page shows the three priced ways out as cards, with the two plain actions as buttons below them.

## Phase 22 — Destination Intelligence Agent

> Build log: `docs/phase22_build_log.md`. Prompt: `prompts/destination_intelligence_v1.md`. The numbers in this section were measured on the machine it was built on.

132. **The fourth agent asks Groq's large model at low reasoning effort — not Claude Haiku, and not the small model.** The roadmap names Claude Haiku 4.5; the app has no Anthropic key and needs none (#67). The choice among what it has was measured. Groq's free tier allows 8,000 tokens a minute *per model*, and a plan already spends about 4,000 of the large model's on the builder alone, with the preference extractor after it. The small model has its own allowance, so it was tried first: at its default effort `gpt-oss-20b` spent its 2,048 tokens reasoning and returned nothing, or a reply cut off halfway; at low effort it answered in a second but put Leh's Stok Palace in Kaza and Delhi's Chandni Chowk in Varanasi, and one reply was not valid JSON. `gpt-oss-120b` at `reasoning_effort="low"` names the right places in about 1.5 s for about 900 tokens — the answer is recall, not reasoning. One attempt, no retries, 8 seconds at most. Gemini is left alone: its 20 requests a day are intent parsing's.

133. **It runs beside the hotel and activities searches — after the budget check, not beside the flights.** The roadmap says "in parallel with the other three". Flights go first because the budget check needs them (#17), and a trip that check stops has no use for local tips: beside the flights, every budget conflict would pay for a call it throws away. Beside the other two it costs no time: on a live Jaipur plan it took 1.5 s of the 5.2 s the searches took. It is not one of the searches the page counts: it publishes nothing on the stream, and `/status` still says "3 of 3".

134. **Its reply is cut down to five shapes, and the plan's model never sees it.** Nothing here can be checked against a source, so nothing is trusted: `coerce_intelligence` keeps strings only, one line each, a tip at most 240 characters, a list at most five items, six places — and drops every other key. The trip goes to the model as JSON in the user message, apart from the instructions; a "destination" that was an instruction came back `{"unknown": true}`. The roadmap has the builder "incorporate" the output. Here code does: `ItineraryBuilder.run` attaches it to the draft once the draft has passed its checks, and a `local_intelligence` key in the plan model's own reply is dropped. Passing it through that model would cost its tokens and let it be rewritten — or let unverified advice decide the plan. The price: the plan's morning / afternoon / evening slots do not follow `best_times`.

135. **A plan never depends on it.** No key, a rate limit, a slow answer, a reply that is not JSON, a place the model does not know: each ends as an `agent_runs` row marked failed with a code — and a plan that is otherwise whole, saved as `completed`, with nothing on the page saying anything failed (roadmap: "section simply absent"). A crash inside the agent costs the tips too, not the plan.

136. **Tips belong to the place, so they are carried forward — and a plan without any gets them with its next change.** A targeted refinement or a retry keeps the tips without asking again, and so does "add a day"; a full re-plan may be for another place or season and asks again. A plan that has none — made before Phase 22, or on a day the model did not answer — gets them beside the search its next targeted change repeats, and the assistant says "Local tips added". A place the model said it does not know is not asked about again.

137. **They are shown as what they are: general advice, to check locally.** Both models said the Anjuna flea market is on Saturdays; it is on Wednesdays. The section opens with where it comes from — "the assistant's own knowledge of Goa, not a live source" — and the PDF says the same. A `best_times` place that is one of the plan's stops is marked "In your plan · Day 1 · Morning" and listed first; the match is by the words of the name ("Aguada Fort" is "Fort Aguada"; "Fort" alone is not).

138. **An accordion of our own, not shadcn/ui.** The roadmap names shadcn/ui's Accordion. The project uses neither shadcn nor Radix (#89 made the same call for the toast), and this is its only accordion: `LocalTips.tsx` is the WAI-ARIA pattern in about a hundred lines — each heading a button with `aria-expanded` and `aria-controls`, its panel a region labelled by it — closed until asked for, several open at once, keyboard by way of the buttons.

139. **The PDF prints the tips too.** Phase 19's rule is that paper and screen agree (#103): an itinerary with tips gets a "Local tips" page after the days, with the page's five headings (a test reads them out of `lib/tips.ts`) and the same note on where they come from. Stored tips are read as forgivingly as the rest of an itinerary, and a plan without any prints exactly as before.

## Phase 23 — pgvector Similarity Search

> Build log: `docs/phase23_build_log.md`. The experiment: `scripts/embedding_experiment.py`. Every score in this section was measured on `gemini-embedding-001` at 1536 dimensions and belongs to it.

140. **The summary that is embedded says what kind of trip it is — and the roadmap's guess about it was wrong.** The roadmap has similarity use the "structured summary" Phase 14 stored (`"Goa 4 days 42,000 INR mid-range. Top activities: …"`), expects it to beat the full text, and asks that both be tested. Twelve itineraries of five kinds (beach, mountains, heritage, spiritual, nature) and six queries were embedded each way:

    | Text an itinerary is embedded as | task type of a stored text | same kind among a trip's 3 nearest (of 22) | Goa nearer the Andamans than Ladakh by | right among a query's 3 nearest (of 14) |
    |---|---|---|---|---|
    | full text (every slot and hotel) | none | 17 | +0.056 | 13 |
    | | RETRIEVAL_DOCUMENT | 17 | +0.029 | 13 |
    | | SEMANTIC_SIMILARITY | 21 | +0.036 | 14 |
    | Phase 14's summary | none | 17 | **−0.021** | 13 |
    | | RETRIEVAL_DOCUMENT | 17 | **−0.018** | 14 |
    | | SEMANTIC_SIMILARITY | 18 | +0.003 | 14 |
    | new summary + length and cost | none | 20 | +0.035 | 13 |
    | | RETRIEVAL_DOCUMENT | 22 | +0.028 | 13 |
    | | SEMANTIC_SIMILARITY | 21 | +0.034 | 14 |
    | **new summary** | none | 20 | +0.057 | 14 |
    | | **RETRIEVAL_DOCUMENT** | **22** | +0.028 | **14** |
    | | SEMANTIC_SIMILARITY | 22 | +0.054 | 14 |

    Phase 14's summary was the worst text of the four: with it a Goa beach trip is nearer a Ladakh trek than the Andaman beaches — the roadmap's own counter-example. It opens with the destination, a length, a cost and a budget word, and those are what two trips then have in common: Goa and Ladakh were both "mid-range", the Andamans "luxury". The full text does no worse than it, diluted as it is by dates and hotel names. The new summary — `"beach and food trip to Goa. Kinds of places: beach, history, spiritual. Places: Baga Beach, …"` — puts the traveller's interests and the kinds of places first and says nothing of the trip's size: every one of the 22 neighbours is right. Adding the length and the cost back costs a search result. So a summary does beat the full text, but only once it is a summary of the right thing. The full-text row is still written (Phase 14's two rows per itinerary), now labelled; nothing reads it.

141. **A stored summary is embedded as a document, a typed query as a query — and "nearest" is not "near".** The model takes a task type. The three pairings tried came out within noise of one another on twelve trips (the table above; without any, 20 of 22), so the one the model documents for the case was taken: `RETRIEVAL_DOCUMENT` for what is stored, `RETRIEVAL_QUERY` for what is typed; two trips are compared document to document. Vector search always has an answer, so each use has a cut-off, read off the same run: two trips of the same kind scored 0.850–0.906 and two of different kinds 0.782–0.859, so a trip is "similar" from **0.84** (all 11 same-kind pairs kept, 4 of 55 others let in — near misses such as Hampi's temples and Varanasi's). A real query's best match scored 0.614–0.730 and a nonsense one's ("quarterly tax return") 0.478–0.554, so below **0.58** nothing matches; above it the answer is the trips within **0.04** of the best (for thirteen queries: 30 right, 4 wrong, 2 missed). Twelve trips and thirteen queries are a small sample: the numbers are constants in `app/search.py` with this reasoning beside them, to be measured again with the model or the text.

142. **HNSW, not IVFFlat — over the summaries only, and the planner decides when to use it.** IVFFlat sorts vectors into lists around centroids it computes when the index is built: it wants the data there first (migration 001 creates the index on an empty table), and its recall falls as new rows drift from those centroids until it is rebuilt. HNSW builds a graph row by row — no training step, good from the first insert, better recall for the same speed — and pays for it in memory and slower inserts. A table that starts empty and grows by two rows a plan is the case for HNSW; pgvector's defaults (`m` 16, `ef_construction` 64) stand. The index is now partial, `WHERE kind = 'summary'`: only summaries are searched, and in an index over both kinds half of every neighbourhood would be full texts the query then discards. For one traveller's few dozen trips the planner does not use it at all — it picks that traveller's rows out by their own indexes and sorts them, which is exact and cheaper. When it does walk the HNSW index, the index hands back its nearest vectors whoever they belong to and the conditions are applied afterwards; with other people's trips nearer, a traveller's own would all be filtered away. `hnsw.iterative_scan = strict_order` (pgvector 0.8) makes the scan go on until the limit is met — tested with seventy nearer trips of someone else's and the index forced.

143. **Similar trips and search are over the traveller's own trips, never anyone else's.** The roadmap says "similar past itineraries" and that clicking one "opens that itinerary". An itinerary says where someone is going and on which dates; shown to another account it is a leak, and there is no page on which another account could open it. Both queries carry `user_id` in their `WHERE`, and a test puts a stranger's nearer trip in the table. Trips shared on purpose would be a feature of their own.

144. **One result per trip: its latest itinerary, and only a plan that stands.** Every refinement saves a new itinerary with embeddings of its own (#35). Compared naively, a trip would be its own nearest neighbour several times over, and be found by a plan it no longer has. Both queries keep only the row whose itinerary is the trip's latest, and only trips that are `completed` — or `planning`, which with an itinerary means a change in flight and the old plan still on the page.

145. **`embeddings.kind`, and the old vectors made again (migration 004).** Phase 14 wrote an itinerary's two vectors with nothing to say which was the summary. The migration adds `kind` and drops what was stored: the two cannot be told apart reliably, and the summaries among them are of the text that ranks trips badly (#140). In their place each trip's latest itinerary — the only one searched — gets a `pending_retry` row, which is the mechanism Phase 14 already had for "embed this again" (#31). Startup recovery now makes them one itinerary after another instead of all at once: the embedding API's free tier answered a burst with 429s (the experiment had to wait it out several times).

146. **Search matches by meaning, embeds the query once, and can say "nothing".** `GET /trips/search?q=` embeds what was typed — one attempt, eight seconds: a request is waiting — and keeps the vector in Redis for a day under the model's name, so the same words typed again cost no second call; without Redis it simply asks each time. When the query cannot be embedded the answer is 503 with words for the page, not an empty list that would read as "no trips match". An empty list is its own answer (#141). What it does not do: arithmetic. In the roadmap's example, "beach under 50k 5 days", "under 50k" and "5 days" are words to an embedding — the live run returned a ₹95,000 trip among the beaches — and the roadmap gives those limits their own parameters in a later phase. The route is declared before `/{trip_id}`, or "search" would be refused as a malformed id.

147. **A plan is not embedded the moment it is saved, so `/similar` can answer "pending" — and the page asks again.** Embeddings are made in the background after `planning_complete` (#53). The trip page shows a plan at once and asks for its similar trips at once; on the live run the first two answers were `pending` and the third, a second later, had the results. The page retries three times, each a little later, and then stops. Like the local tips (#135) the section is an extra: nothing alike, an error, or an embedding that never came all look the same — no section.

148. **The trip a card is named by is its most popular stop.** The roadmap asks for "one activity highlight" on a thumbnail. `highlight()` takes the stop with the highest popularity rating (#83), the first of them when several tie, and never free time.

149. **The test stacks get an embedder that counts words, cut-offs of its own, and a cache of its own.** `tests/fakes.word_vector` gives every word a dimension, so two texts are as close as the words they share: enough for "the Goa and Varkala plans are alike and the Leh one is not" to be true in the browser without a model. Its scores are on another scale, so `network_stubs` sets cut-offs to match. The first version hashed words into the 1536 dimensions and "zzzz" matched a trip by collision; and the query cache — Redis, shared with the dev servers like the map tiles of #109 — handed a later run an earlier run's vectors. The stand-in now has a model name of its own per process, which is what the cache key carries.

150. **A demo account for seeing it.** Similar trips need trips to be similar to, and planning a dozen by hand costs an afternoon and the day's model quota. `scripts/seed_demo_trips.py` gives `demo@example.com` the experiment's twelve itineraries, embedded by the real model exactly as a planned trip is. It touches only that account.

## Phase 24 — Caching & Rate Limit Handling

> Build log: `docs/phase24_build_log.md`. Three things here are not in the roadmap's entry and came out of doing it: the tools were running one at a time (#155), a flight or hotel search was cached under its budget (#156), and none of the app's own INFO log lines were being shown (#160).

151. **The limits are the providers' own, not the roadmap's.** The roadmap names Amadeus at 60 a minute, Google Maps at 100 and OpenWeather at 60. Two of those providers were replaced long ago (#64–72), so each limit was read off the provider that is actually called — from its response headers where it sends any:

    | Provider | Limit kept | Where it comes from |
    |---|---|---|
    | Duffel (flights) | 30 a minute | `ratelimit-limit: 30` on `POST /air/offer_requests`; the count resets on the minute. (`GET /air/airlines` says 4,000: the limit is per endpoint, and the search is the tight one.) |
    | LiteAPI (hotels) | 5 a second | `x-ratelimit-limit: 5` |
    | OpenTripMap (attractions) | 10 a second | `x-ratelimit-limit: 10` |
    | OpenWeatherMap | 60 a minute | no headers; the free plan's documented limit — the one number the roadmap had right |
    | Nominatim (geocoding) | 1 a second | no headers; the usage policy of the public server |

    Three of the five are per *second*, which "calls per API per minute" would not have kept. The window slides — no stretch of a period holds more than the limit — which is never looser than Duffel's count per calendar minute. And it is a tenth longer than the provider's: a request is counted here when it leaves and there when it arrives, so two sent a window apart can arrive a little closer.

152. **The limiter is in the MCP server, not in the client.** The roadmap puts it in `src/ai/mcp_client/rate_limiter.py`. The client sees tool calls, and a tool call is not a request to a provider: a cache hit is none, a hotel search is one or two (a region falls back to a radius search), an attractions search is one per kind of interest plus a place lookup of one or two. A limiter that counted tool calls would hold a cache hit in a queue and wave three requests through as one. It is `src/ai/mcp_server/rate_limiter.py`, and the turn is taken at the one place a request leaves (`outbound.send`), after the cache has been read. The count is in that process's memory: one backend process runs one MCP server. With several backend workers each would count alone, and the windows would have to move to Redis.

153. **A request over the limit waits its turn; a queue a whole window deep is refused.** `acquire()` gives each caller the earliest moment that keeps the limit, in the order they asked, and sleeps until then — three callers at a one-a-second limit are spaced a second apart rather than all released together to race. Waiting is the roadmap's rule ("queue it and wait rather than failing") and it has one bound: 60 seconds, a whole window of the slowest limit. Inside that every request gets its turn; a request that would wait longer — the sixty-first flight search within a minute — is answered `RATE_LIMITED` at once instead of being held for two minutes behind a page that shows nothing.

154. **Backoff with tenacity, as specified — around every provider request, and only for answers a second try can change.** `wait_exponential_jitter(initial=1, max=30)`, `stop_after_attempt(4)`: waits of 1–2 s, 2–3 s, 4–5 s. Retried: HTTP 429, 500, 502, 503, 504, and a connection that was never made. Not retried: any other 4xx (a wrong key stays wrong) and a read timeout — the provider had the request and its full time, and three more 30-second waits would hold a traveller for minutes. When a 429 says how long to stay away (`Retry-After`, or Duffel's `ratelimit-reset`), that is the wait if it is the longer one, capped at the same 30 s. Every wait is a log line — `[BACKOFF] duffel: HTTP 429 — waiting 1.30 s before attempt 2 of 4` — because a retry nobody can see is just a slow search; the line names the status or the error's type and never its text, which holds the URL and, for two providers, the key. A 429 that outlasts the four attempts is `ToolError(code="RATE_LIMITED")`: the traveller reads "This search is busy right now. Try again in a minute." beside a Retry button, since for this failure trying again is exactly what helps. The LLM and embedding calls keep the policies they have: the embedder already uses this one (Phase 14), and a chat model that is rate limited is answered by another model, not by waiting (#69).

155. **The tools now run in threads — they had been running one at a time.** FastMCP calls a plain function on its event loop (`func_metadata`: `return fn(**args)`), and every tool blocks on an HTTP request. So the hotel and attractions searches a plan sends together were made one after the other, and no answer left until the loop was free: on the Phase 22 live run the two agents both "took" 5.2 s and finished in the same millisecond. With waits for a rate limit and backoff about to be added to those blocking calls, one queued flight search would have frozen every other tool. `server.threaded()` registers each tool as a coroutine that hands the same function to a worker thread; the name, description and schema FastMCP derives are identical (a test compares them). Three searches at once, same city, cold cache, on the real providers:

    | | flights | hotels | attractions | all three done |
    |---|---|---|---|---|
    | before (`main`) | 5.74 s | 7.39 s | 7.40 s | 7.40 s |
    | | 2.13 s | 3.93 s | 3.94 s | 3.94 s |
    | after | 2.27 s | 0.80 s | 1.83 s | 2.27 s |
    | | 1.23 s | 0.82 s | 1.61 s | 1.61 s |

    What that asked of the code: the limiter and the cache's Redis connection take a lock, and the geocoder's one global lock became a lock per place (#157).

156. **A flight or hotel search is cached by what the provider is asked, not by what the tool was called with.** The key was the whole tool input. For flights that included the budget and the preferred airlines, neither of which Duffel is ever told; for hotels, the nightly budget — what is left after the flights, so a different number on every re-plan of the same stay, and unknown until the flights are back. The same question was being asked of the provider again under another key, and a hotel search could not be warmed at all. The key is now the airports, dates, passengers and connections allowed (so "Goa" and "GOI" are one search, and a re-plan that allows another stop is still its own); for hotels the place, dates and guests. What is stored is the provider's five cheapest results, and the budget and the airline preference are applied to them after the cache is read. Five are enough: of the offers within any budget, the cheapest five are always among the cheapest five of all — a test checks it against the full list for seven budgets. An answer with nothing in it is not kept, so the next search asks again.

157. **One search per cache key at a time.** Two identical searches that start together both miss the cache and both go to the provider — and warming a trip while its planning starts is exactly that. `cache.single_flight(key)` holds the key while its answer is fetched: the second caller waits, then finds the answer cached. Different keys never wait for each other, and a search that fails releases its key. This replaced the geocoder's single process-wide lock, which was doing two jobs: keeping Nominatim to one request a second (now the rate limit's) and stopping the hotel and attractions searches from both looking the same place up (now this).

158. **Cache warming makes the searches planning will make, with planning's own code.** On `POST /trips` a background task starts the trip's opening searches; the request is answered first (31 ms on the live run). The roadmap names flights and weather. Hotels are warmed too — possible since #156 — and attractions when the trip names its interests; with none, planning asks the traveller for them or reads them from the request, and that search is not known yet. A warmed entry under the wrong key is a wasted request to a rate-limited provider, so the parameters come from the functions planning uses (`orchestrator.flight_search_input`, the agents' `*_tool_params`), with the traveller's saved preferences applied as the graph applies them: the origin is the saved home city, else Delhi. A test runs the real tools behind fake providers, warms, then runs a plan's searches and requires that no provider hears from it again; another starts planning while warming is still at the provider and requires one request, not two (#157). Not warmed: a trip whose destination is a sentence — where it goes is only known once planning has read it. A plan whose request names another origin simply misses. Weather is warmed as the roadmap says though nothing reads it before Phase 38; beyond five days out it is a climate estimate and costs no request. Each trip created costs a flight search of Duffel's thirty a minute whether or not it is ever planned, so there is a switch: `CACHE_WARMING_ENABLED`.

159. **The TTLs match the Phase 3 spec; nothing needed correcting — except the command that was meant to check them.** Read back from Redis with `TTL`, seconds after the entries were written (live run: 280, 880, 21,581 and 3,579 s, twenty seconds in):

    | Cache | Phase 3 spec | In Redis |
    |---|---|---|
    | `mcp:flights:*` | 5 min | 300 s |
    | `mcp:hotels:*` | 15 min | 900 s |
    | `mcp:attractions:v2:*` | 6 hr | 21,600 s |
    | `mcp:weather:*` | 1 hr | 3,600 s — forecasts and climate estimates alike |
    | `mcp:geocode:v2:*` | not in the spec | 2,592,000 s (30 days): places do not move, and Nominatim asks its users to cache (#72) |

    The roadmap's check is `TTL mcp:flights:*`. `TTL` takes one key, not a pattern: that command answers `-2`, "no such key", whatever is cached — it would have "verified" an empty cache. `scripts/cache_ttls.py` reads every key of every family, compares it with the spec (written out in the script, not imported from the code it checks), and exits 1 for a key that never expires, outlives the spec, or belongs to a family nobody set a TTL for. The integration test reads the same values from a real Redis.

160. **The app's own INFO log lines are now shown.** The acceptance line is "visible in logs: `[CACHE WARM] flights:...`", and at first it was not: uvicorn configures the `uvicorn` loggers and nothing else, so everything the app or the planner logged at INFO went nowhere. `[EMBEDDING RECOVERY]` had been written at every restart since Phase 14 and never once displayed. (The `[CACHE HIT]` lines were visible only because they come from the MCP subprocess, where FastMCP sets logging up.) `main._show_app_logs()` gives the `app` and `src` loggers a handler in uvicorn's own layout — only when nothing else handles the root logger, so a deployment with its own logging config, and pytest, are left alone.

161. **Tests run the real tools behind fake providers, and none waits or warms unless it means to.** `tests/fakes.FakeProviders` stands in for `httpx.get` / `httpx.post` and answers as the five providers do; it counts what it receives, can be told to turn requests away, and can count in real time as a provider does, answering 429 past its limit. `tool_server()` puts the real client and the real FastMCP server in one process — threads, cache keys, limits and backoff are the ones that ship; only the transport is in memory. That is what the roadmap's scenario runs on: three agents at once against a provider that allows two requests a window, zero 429s. Three autouse fixtures keep every other test honest: rate-limit and backoff waits are recorded instead of slept through, the limiters start each test empty (the thirty-first flight search of a run would otherwise be held a minute), and creating a trip starts no background searches. The integration tests point the tools' cache at Redis database 15, so a developer's cached searches are neither read nor overwritten with fake flights.

## Phase 25 — Group Trip Intelligence

> Build log: `docs/phase25_build_log.md`. The experiment: `scripts/group_experiment.py`. Three things here are not in the roadmap's entry and came out of doing it: the attractions provider has no spas and no category called "spas" — asking for one failed the whole search (#163); an interest with no well-known places found nothing at all, and food is such an interest nearly everywhere (#164); and the model that writes the plan is asked for balance but is not what guarantees it (#167).

162. **A group is its travellers: a name and what each enjoys — and they are optional.** `trips.group_members` (migration 005) holds `[{"name", "interests"}]`, two to nine of them. Left out, a trip is planned exactly as before, for `group_size` people who share `interests`: every existing trip, and every test of one, is untouched. Given, the travellers are counted (`group_size` is their number unless more are said to be coming — two adults with opinions and two children is a group of four), and the trip's `interests` become everyone's, so that whatever already reads them — the clarifying question, the local tips, the embedding a trip is searched by — works without knowing about groups. A traveller with no interests is one of the party and happy with what the others choose. Names and interests are shown to the model that writes the plan, so both are a few plain words in any script: letters, their marks and digits, spaces and a little punctuation — nothing that could close a JSON string or start a new line.

163. **"spa" is searched as nothing, and said to have found nothing.** The roadmap's fourth traveller wants "spa, relaxation". OpenTripMap has no spas near any of five destinations tried — and no kind called `spas`: the request is answered HTTP 400, "Unknown category name". Since Phase 3 the interest "wellness" had been searched as exactly that kind, so a trip with it lost its *whole* attraction search to `OTM_ERROR`; "wellness" was also one of the suggestions on the new-trip form. Both are now mapped to no kinds at all: the search skips them, the member's result says `nothing_for: ["spa"]`, and the page says "Nothing was found in Goa for: spa" under that traveller's name. The alternative — quietly giving a spa lover gardens and calling them his — would have made the plan look better than it is. "relaxation" is searched (beaches, gardens, water, viewpoints). The form's suggestion is now "relaxation". Every kind in the table was checked against the live catalogue, and a test holds the list, so a kind the provider does not know cannot be added again unnoticed.

164. **An interest with too few well-known places is filled up with lesser-known ones; and "adventure" is no longer stadiums.** The search asked only for places of popularity 2 and up. Counted live (well-known / any, of 10 asked for):

    | | Goa | Manali | Rishikesh | Kochi |
    |---|---|---|---|---|
    | food (`foods,restaurants,cafes`) | 0 / 10 | 1 / 10 | 0 / 10 | 2 / 10 |
    | shopping (`shops`) | 0 / 10 | 0 / 8 | 0 / 7 | 10 / 10 |
    | adventure, as it was (`amusements,sport`) | 1 / 3 — a cricket stadium | — | 0 / 2 — a stadium | 4 / 10 — stadiums |
    | waterfalls | 1 / 3 | 0 / 10 | 0 / 2 | 0 / 0 |
    | peaks, caves (`geological_formations`) | 1 / 2 | 4 / 10 | 0 / 4 | 0 / 4 |
    | reserves (`nature_reserves`) | 2 / 4 | 1 / 5 | 1 / 1 | 1 / 2 |

    A traveller who said "food" got no food stop in three places out of four — on any trip, group or not. Now each interest is searched among the well-known first and, when that returns fewer than asked for, again among all of them, the lesser-known going after the well-known (one more request, only for an interest that needs it). They are described as "lesser-known" and carry their real rating. "Adventure" is searched as what the provider has that an adventure is made of — peaks and caves, waterfalls, reserves, climbing, the water sports, the slopes, amusement parks. And the cut at the limit now takes one place from each interest in turn: three interests and ten places used to mean four, four and whatever fitted of the third.

165. **Each traveller's interests are searched on their own, and every place says whose interest it answers.** Roadmap: "call `get_attractions` once per member's interests, merge results, de-duplicate". The calls run at once (the tools run side by side since Phase 24), each with the tool's full limit of ten: the provider answers nearest-first, and at six a traveller who likes history got the three sights by the station and never the fort on the hill. What makes the merge possible is new in the tool: every attraction carries `interests` — the ones asked for that it was found under. A place suits a traveller when one of those is theirs; found in two travellers' searches, it is kept once and suits both. A member whose search finds nothing is not a failed search: the others keep theirs and the plan says whose came up empty. A search that fails for any other reason fails the whole search — half a group's places would be a plan that looks balanced and is not, and the page offers a retry. Searched as one traveller on `main`, the roadmap's group got 4 to 10 places (in Rishikesh four, none of them for the traveller who wanted food or the one who wanted adventure); member by member it gets 12 in all five destinations, with at least two for everyone.

166. **`score_activity_for_group` is the share of the group a place is for — and the ranking by it is not what picks the places.** A member's relevance is 1 when the place answers one of their interests and 0 when it does not; the score is the average over all the members, so a beach two of four asked for is 0.5. The roadmap says "rank by average relevance across all members". Ranked by that alone, a pool is whatever most of the group shares and then whoever's interests the provider knows best — four heritage forts before the one waterfall, because popularity breaks the ties. So the places a plan is made from are *taken in turns*: each time for the member who has the fewest so far, the best-ranked place left that suits them; a place for two counts for both (`pick_for_group`). The order is kept, and it matters as much as the choice: a plan filled from the top of that list, two or three stops a day, has something for everyone by the second day. How many places: one for each member in each two days and one over, between 10 and 20.

167. **The model is asked for a balanced plan; code makes it one.** Roadmap: "ItineraryBuilder updated: day slots balance across member profiles". The prompt now names the travellers, marks each attraction with who it suits, and asks for at least one stop for each of them in every two days (`prompts/itinerary_builder_v9.md`). On the live run the model did exactly that. But a rule that matters is not left to a model's goodwill — the same reason the evaluator is plain code (#21): after the model's reply has passed the data-scope check, `group.rebalance` goes through the plan two days at a time, and for every traveller with nothing in them puts a place in — one that suits them and is not in the plan yet, into an empty slot, or in place of a stop those days can spare; failing that, one of their own stops brought over from days that have two. A stop is only ever given up where everyone it suits has another in those days, so each change gives someone two days they did not have and takes none from anyone: it ends, and running it twice changes nothing more. Who a stop is for is then copied onto the slot from the attraction — never taken from the model, which is also not allowed to write `group` or the per-person figures. "Two days" are the days in pairs, an odd last day joining the pair before it: the day of the flight home could not hold a stop for each of four people.

168. **"As far as the places found allow" — and what was not found is said.** Nobody can be given a waterfall the provider does not list. A traveller whose interests found nothing, or whose places are all in the plan already, is not a failed plan: the evaluator's new check (`unbalanced_group`) fails only a gap that an unused place would fill — which, since the builder repairs exactly those, means the repair was bypassed. The itinerary carries a summary (`structured_data["group"]`): for each traveller the stops that are theirs and the interests nothing was found for, and `balanced` — true only when every traveller really has a stop in every two days, not when the plan merely could not do better. The page shows it as it is: "Something for everyone, every two days", or "Not everyone could be given a stop every two days" with the reason beside the name.

169. **The cost is split equally, whoever a stop is for.** The roadmap asks for "individual cost shares". The group goes to the fort together and shares the rooms, so each traveller's share is the same: `per_person_cost` is the plan's total over the number travelling, and `per_person_breakdown` what it is made of — one traveller's part of the flights, the stay and the activities — with a share for each traveller by name, in whole rupees that add up to the total exactly (when it does not divide, the first named carry the odd rupee). All of it is worked out by code from the checked plan (`pricing.per_person`) and saved at the top level of the itinerary; a trip of several travellers who were not told apart gets it too, as "Traveller 1 … 4". The roadmap's test — `total_cost / group_size ≈ per_person_cost` within ₹100 — holds to the paisa. `estimate_budget` takes `group_size` and returns the same breakdown; its `per_person` had been the whole total since Phase 3, with a comment saying this phase would fix it.

170. **On the page: the share beside the total, a name on every stop, and a panel that says how it turned out.** "₹16,834 / person" stands under the total in the cost card, for any trip of more than one. The page and the PDF divide the total by the travellers themselves — the sum the itinerary carries as `per_person_cost` — so a plan saved before this phase shows its share too. (They first preferred the saved figure and fell back to dividing; breaking that on purpose changed nothing, because the two are one number by construction, and the branch was removed.) Each stop says "For Asha and Dev". "Who it is for" lists the travellers with their interests, their stops, and what was not found. The PDF agrees (#103): the share on the cover under the total, "For …" among each stop's facts; its cost page had printed a "Per traveller" row since Phase 19. The new-trip form keeps its one interests field; "Do they want different things?" opens a row for each traveller, and "Everyone shares the same interests" closes them again.

171. **A change to a group's plan keeps the group in it.** The travellers are part of the saved planning state, so "add a day", a full re-plan and a retried search all start from them. A change to the hotel or the flights rebuilds the plan from the places it already uses, each still saying who it is for. A change that names what to look for ("add some museums") is one search for that, not every member's again — the finds say whom they suit and join the places in the plan. The balance is kept over the request: asked to "swap the beaches for museums", the plan ends with museums and still one stop for the traveller who came for the beach.

172. **Cache warming and the test stacks follow.** A group's attraction searches are warmed member by member — the calls are built by the function planning uses (`attraction_searches`), and Phase 24's test that a plan after warming asks no provider anything now runs for a group too. The fake provider answers by kind and popularity from a catalogue and says 400 to a kind it does not know, as the real one does; the roadmap's acceptance test runs on it through the real MCP server, the real agent and the real builder. The attraction cache key moved to `v3`: a search returns other places than it did, and each says what it is for.

## Phase 26 — LangSmith Tracing & Token Costs

> Build log: `docs/phase26_build_log.md`. The local stand-in for LangSmith: `scripts/trace_receiver.py`. Three things to know before the entries. The phase was built without a LangSmith key and verified on **what the planner uploads** — read by the tests, and by a local receiver on a real run (#179); run against LangSmith itself after the merge, it turned out that every plan's trace went to the wrong project, which is fixed, and the acceptance has been read back from LangSmith since (#189). The dollar figures are the providers' own list prices as of 2026-10-11; the first table, from price trackers, had two models of three wrong (#181, #190). And at those prices the roadmap's alert — $0.10 for one trip — is forty plans, not ten retries (#184).

173. **Tracing is switched on by the app, from its own settings — not by the tracing library, from the environment.** Roadmap: "`LANGCHAIN_TRACING_V2=true`, `LANGCHAIN_API_KEY` in `.env`". LangChain reads those two from the process environment by itself; this app reads `.env` into a settings object and never exports it, so run with `uvicorn` the two lines in `.env` would have switched on nothing, and under `docker compose` (which does export them) they would have. `tracing.configure(settings)`, called once when the app starts, makes it one rule: on when the switch is true **and** there is a key; and it says so in the log — "LangSmith tracing is on — project 'tripplanner-ai', sent to …" — or says why not. The switch without a key is off, with a warning, rather than a planner that tries to upload and is refused on every run. `APP_ENV=test` is off whatever `.env` says: the test stacks plan dozens of trips and none belongs in anyone's project. And off is said to the library too, so a `LANGSMITH_TRACING=true` left in a shell cannot trace behind the settings' back. `LANGCHAIN_PROJECT` names the project; `LANGCHAIN_ENDPOINT` is for another LangSmith — the EU one, a self-hosted one, or the local stand-in.

174. **A node is a span because LangGraph makes it one; code adds a span only where a node's name does not say enough.** Roadmap: "Every LangGraph node execution is a span: input, output, duration, token count". With tracing on, LangChain records every graph node and every model call by itself — the node with its state in and out and its times, the model call with its prompt, its reply and its tokens. Four things a name alone did not say, and each is now a span of its own (`tracing.span`): that a flight search is a **re-plan** — "re-plan 1: cheaper flights", "re-plan 2: …", with the cap and the stops it was allowed; which pass of the evaluator's loop this is — "**evaluator retry 1**", "evaluator retry 2", with the checks that failed, so how often a plan was sent back is read off the names; which **tool** was called — "mcp:search_flights", with what was asked and what came back; and the tips agent, which is not a graph and would have been an unnamed model call. Each agent's own graph is named for its agent (`flight_agent`, not "LangGraph"). The token count of a step is the sum of the model calls inside it — LangSmith adds them up the tree, and so does the local reader.

175. **A trace is found by its trip: `trip_id` and `user_id` are metadata on the root, and every span beneath inherits them.** Set once, on the run's config (`tracing.run_config`); LangChain hands a run's metadata to everything made inside it, so the filter `metadata: trip_id = …` returns every decision made for one trip — the plan, each change to it, each retried search — and nothing of another's. Beside them: `kind` (plan, replan, refine, retry, classify), `turn`, and for a change which one (`detail`). The same as tags (`trip:<id>`, the kind) for the tag filter. The trace's name says what it is: "plan trip", "replan trip: cheaper_flights", "refine trip: targeted_hotel", "retry trip: activities_agent", "classify refinement". `user_id` is the account's id — never the email address.

176. **A change to a plan is a trace of its own, with the graph's steps.** A refinement or a retried search does not invoke the graph: it calls its nodes one by one, in an order the request decides. Untraced, those would have been loose model calls. `tracing.root` opens the trace, and `tracing.step` makes each node call the span the graph would have made of it — `build_itinerary`, `evaluate`, `retry_dispatch`, `persist`, `merge` — so a change reads like a plan does. Reading what a change asks for (the classifier) happens before any of it, in the request itself, and is a small trace of its own under the same trip and turn.

177. **What is uploaded is what the planner saw and wrote — and nothing that is not data.** A run's state carries three live objects: the database session and two callbacks. LangSmith's client is built with `hide_inputs` and `hide_outputs` set to `scrub`, which takes exactly those three keys out of every run before it leaves; a test reads the upload and finds no trace of them. API keys are not in it: LangChain writes a model's key as a placeholder that names the variable (`{"type": "secret", "id": ["GROQ_API_KEY"]}`), and the LangSmith key travels in a request header only. On the real stack the whole upload of two plans and a change — 78 runs, 504,527 characters — was searched for every secret value in `.env` (eleven of them), for an email address and for a bearer token: none. What **is** uploaded is the trip: the destination, the dates, the budget, the travellers' names and interests, the prompts and the plan. That is the point of a trace, and it is why tracing is the operator's decision, off by default, and said in `.env.example` in so many words.

178. **Tracing never fails a plan, and never holds up a shutdown.** The library uploads from a background thread: a LangSmith that is down or refuses the key costs a log line, and the plan is made (tested with a transport that fails every request). When the app stops, the traces still waiting are sent — for five seconds at most (`tracing.shutdown`). The bound is there because the library's own `flush()` has none: it waits for a queue that nothing empties once the sending thread has died, and that thread dies quietly when a server's `/info` reply lacks a field it reads — found by the first probe against the stand-in, which hung. On the real stack, pointed at an address nothing listens on: the plan took its usual nine seconds, and the backend stopped 5.3 s after it was asked to, saying the last traces had not been sent.

179. **A local stand-in for LangSmith, and what it does and does not prove.** There is no LangSmith key in this build's `.env`, and the roadmap's four acceptance points are all "in LangSmith". They are verified on the one thing a trace *is* — the records the library sends: `src/ai/trace_tree.py` merges them (a run when it starts, the same run when it ends) into trees, the tests read them through an HTTP transport that goes nowhere, and `scripts/trace_receiver.py` serves the two requests the library makes, prints every finished trace as a tree, and answers `/traces?trip_id=` (what LangSmith's metadata filter does) and `/records` (every run exactly as it was sent). The stand-in asks the library for JSON batches, which anything can read. Told nothing the library sends the same runs as multipart, and to a server that says it takes compression — a current LangSmith, by the library's own account — as zstd-compressed multipart built by different code again; so one test sends a plan down each of those two roads as well, and reads the same trace back, without the live objects. The real backend was run against it: a plan is one trace of 34 spans, a tight budget shows "re-plan 1" and "re-plan 2", a change is two more traces under the same trip. What this does **not** prove is anything about LangSmith itself — that the key is accepted, how its UI draws the tree, that its filter box takes `trip_id`. That is one step with a key, and it is in `HOW_TO_RUN.md`. *(Taken on 2026-10-11, after the merge — and it did find something: #189.)*

180. **Tokens are read by one recorder for the whole process, and credited to the innermost timer.** Roadmap: "Extract token usage from LangChain callback and write to DB". Every reply of a LangChain chat model carries its token counts; one callback handler, attached to every model call by LangChain's own configure hook, reads them (`src/ai/usage.py`). `timed_run()` — which every agent already wraps its work in for the row's duration — now also opens a meter, and the recorder credits a reply to the meter open *where the model was asked*: the innermost one. That is the whole design, and the reason it is not LangChain's stock `get_usage_metadata_callback`: the orchestrator times a run and each agent inside it times its own part, and the stock callback credited both — every token twice, on the first probe. So a row has exactly what its agent spent; the orchestrator's own row has only what no agent was timed for (today: nothing); and a row for work that asked no model — a search, the budget check, the evaluator — has no tokens at all, `NULL`, because "asked no model" is not "0 tokens". Streamed replies are counted (the usage is on the last chunk); a reply that reports no usage adds no claim.

181. **`token_count` is every token in and out; `cost_usd` is the list price, and a model without a price has none.** One number for tokens because that is what the roadmap's column is; the dollars are worked out from input and output separately, per model, so a row that asked two models is still right. The prices are USD per million tokens, kept in one table (`usage.PRICES`): `openai/gpt-oss-120b` 0.15 / 0.60, `openai/gpt-oss-20b` 0.075 / 0.30, `gemini-3.5-flash-lite` 0.30 / 2.50 — the providers' own pages, read 2026-10-11 (#190; as first written, on 2026-10-07, the table came from price trackers and two of the three were wrong). Prices move: correct or add one with `LLM_PRICES` in `.env`, no code change. A dated or prefixed name is priced as the model it is a version of (the longest name on record it starts with). A model with no price — `gemini-3.5-flash`, the code's default `GEMINI_MODEL`, among them — has its tokens counted and its cost left `NULL`, is named once in the log, and shows in the summary as `unpriced_tokens`: a made-up price would make every total wrong and look right. On a free tier nothing is charged at all; `cost_usd` is what the same work costs when it is.

182. **Reading what a change asks for now has a row.** Every refinement starts with a model call that classifies the request, made in the route before any agent runs — so its tokens were on no row, and would have been missing from every total. It is now timed, traced and logged as `refinement_classifier` (shown in the trip's timeline as "Read what the change asks for"). If that row cannot be written the change still goes ahead: a refinement is not refused over bookkeeping. (As first written it was refused — with a 500. Breaking the `except` on purpose changed no test, because no test went down that road; the test written for it failed on the unbroken code: rolling back the failed write expires the trip, and the run was then started on an object that could no longer be read. The trip is reloaded after the rollback.)

183. **`GET /admin/cost-summary?since=YYYY-MM-DD`: in all, by agent, by day.** Counted from `agent_runs`, over the rows that asked a model — `runs`, `tokens`, `cost_usd` and `unpriced_tokens` for the total, for each agent (dearest first) and for each day (oldest first, days in UTC, as the rows are stored). `since` defaults to thirty days back; a date that is not one is a 422. Like the embedding health check it reports on the whole system and shows nothing of any trip, and like it any signed-in user may call it — there is no admin role until the dashboard phase, which is also where this gets a page.

184. **The alert fires once, when a trip's total passes the limit — and at today's prices that is not ten retries.** Roadmap: "single trip total LLM cost exceeds $0.10 → log warning". After a row with a cost is written, the trip's rows are added up (in the database, over every turn), and the warning is logged on the row that takes the total over `LLM_COST_ALERT_USD` — `[COST ALERT] trip …: the models have cost $0.1224 over 2 runs` — not again on each row after. It never raises: the row is written, which is what the caller asked for; 0 switches it off; and the limit is printed as it was set — the first live run, with the limit lowered to $0.002 to see the warning, said "past the $0.00". The roadmap's test is "fires in a test simulating 10 evaluator retries", and it is honest only with a price attached: a build of the plan here is about 6,000 tokens of `gpt-oss-120b` — a quarter of a cent. Ten of them are two and a half cents. So there are two tests: at a frontier model's price ($3 / $15 a million) ten retries cost 61 cents and the alert fires once, on the second; at the prices on record they cost $0.0252 and it does not — and a limit of $0.02 does catch them. On the live run a whole plan cost $0.0025 and a change $0.0020: $0.10 is some forty plans. The evaluator's loop is bounded at three retries a turn, so what this alert really watches is a trip changed again and again, or a price that moved. The default stays the roadmap's; what a runaway looks like on a given model is one line in `.env`.

185. **A tool that could not answer is a span that failed.** The MCP client never raises — a failed call is a returned `ToolError` — so in the first live trace the one search that explained why a re-plan gave up ("no flights within ₹8,250") looked exactly like the searches that worked. The span is now ended with the error (`NO_RESULTS: No flights from DEL to JAI within ₹8,250.`), which is what LangSmith's error filter and the red mark are for. Only that span: the agent handled the answer, so nothing above it failed.

186. **The app's version is read against the README's status line.** Each phase bumps `0.<phase>.0`, and each phase's test of it broke the one before. `tests/unit/test_version.py` now holds the one rule — the version is the phase the README says the project is at — and fails when either is moved without the other.

187. **The tests take the cost settings from the code, and a migration test may not leave its database broken.** Two things about the tests themselves, both learned the hard way. The first: this phase's docs tell the reader to lower `LLM_COST_ALERT_USD` to see the alert, and to correct a price with `LLM_PRICES` — and either line in `.env` would have failed the cost tests on that machine, which read the same settings. A fixture now gives every test the limit and the price table the code ships with. The second: the test that takes migration 006 down and up again restored the schema in a `finally` — but when the downgrade was broken on purpose (it left a column behind), the upgrade in that `finally` failed on the column that was still there, and the test database, which every later run shares, stayed at revision 005 with half the columns. Every breakage tried after that one was "caught" — by the first test that touched the database, whatever the breakage was. The test now drops whatever a downgrade left before it upgrades again, and the break-on-purpose run uses a database of its own and checks it after every breakage.

188. **`langsmith` is a declared dependency.** It had been installed only because LangChain depends on it. The app now imports it itself (`src/ai/tracing.py`), so `requirements.txt` names it, from the version this was written on (0.10.17); the tests also pass on the newest a fresh install brings (0.14.7), which is what CI and the Docker image get.

189. **Every trace is handed its project; none is left to be found.** Run against LangSmith itself for the first time — after the merge, when there was a key — one trip's traces were in two projects: every change to a plan in `tripplanner-ai`, every plan in `default`. The filter on `trip_id` found a trip's changes and not its plan. Two libraries start traces here, and each looks for a project in places of its own. A change is a trace this project opens through the tracing library, which falls back on what `langsmith.configure` was told. A plan is one graph invocation whose trace LangChain starts, and LangChain looks in the context of the task it is running in, then in the process environment, then says "default" — it never asks what `configure` was told; `configure` sets that context only for its caller's task, the app's startup, and this app keeps `LANGCHAIN_PROJECT` in `.env`, which it reads and does not export (#173). So the project and the client are now handed over outright: a plan's graph gets a tracer made with both (`tracing.run_config`), and every trace and span this project opens names both. Nothing local could have shown it — the tests switched tracing on inside the test's own task, which put the project in the one context a request never has; the receiver did not keep projects apart; and under `docker compose`, which does export `.env`, it would have worked by accident. So `tracing.use` now tells the library in a context of its own — whoever switches tracing on sees exactly what a request sees, and with that change alone the existing test failed as LangSmith had shown, `'default' == 'tests'` — and three tests hold the rest: tracing switched on from another thread, as the app's startup is another task; the library made to forget the project it was told; nothing left behind in the caller's context, by switching on or by switching off. The receiver's `/traces` says each trace's project. What stays true: a model asked outside any trace would still be a one-span trace in `default` — there is none today, and a test holds that nothing is traced on its own.

190. **The prices are the providers', and LangSmith's own figure agrees.** The first table (#181) was put together from price trackers: `gpt-oss-120b`'s output at $0.75 a million and `gpt-oss-20b` at $0.10 / $0.50. Groq's own pages say $0.60, and $0.075 / $0.30; Google's says what the table had for `gemini-3.5-flash-lite`, $0.30 / $2.50 with thinking tokens in the output. The second opinion was not looked for: LangSmith prices each model call it is sent from a list of its own, and for each of the seven calls of a live plan and a change it gives, to the sixth decimal, what the corrected table gives (in all $0.004717 against $0.004716; the first table made it $0.005548 — a plan recorded 15% too dear). The tests name the figures on purpose, so a price changed in the table fails a test and gets looked up. `gemini-3.5-flash`, the code's default `GEMINI_MODEL`, stays without a price: the API still serves it (its own model list names it), but Google's price list and documented models no longer do. Rows already written keep the dollars they were given — a row stores its tokens as one number, so a corrected price cannot be applied to it in general.

## Phase 27 — Production Infrastructure

> Build log: `docs/phase27_build_log.md`. Three things to know before the entries. **Nothing here has been deployed to Railway, Vercel, Neon, Upstash or Sentry**: the build had no account on any of them, and everything below is verified on a production-like stack on one machine — the image that is deployed, a TLS-only Postgres behind a pooler in transaction mode, a TLS-only Redis with a password, a receiver for Sentry's reports, the frontend's production build (#207). The roadmap asks for "every missing env var found on first deploy": the code as it was before this phase was deployed onto that stack first, and what it did is the list these entries answer (build log, "The first deploy of the code as it was"). And the worst thing that deploy found was not a variable: the image had installed newer libraries than any test had run on, and the first request that wrote a row answered 500 (#196).

191. **The app says what a deployment is missing — all of it, by name, before it starts — and in production refuses the repository's defaults.** A first deploy fails one variable at a time: start, stack trace, set it, deploy again. Deployed without any, the old code died in the migrations with `connection to server at "localhost", port 5432 failed`; given a database it started and stayed up, broken, with the signing secret that is printed in this repository, `APP_ENV=development` (every SQL statement and its parameters in the log) and a CORS list of `localhost`. `python -m app.preflight` reads the settings the way the app will and lists everything at once — what stops a deployment (`JWT_SECRET` the default or short; a database or Redis on this machine; a Redis URL that is a REST address, or plain `redis://` to Upstash; a CORS list with no deployed frontend in it; no `GROQ_API_KEY`, without which no plan can be written) and what only degrades it (a provider's key missing, no `SENTRY_DSN`). It names variables and never prints a value. The image runs it before anything else, the app runs it again as it starts (`enforce`), and it can be run on a file of values before they are given to a platform (`--env-file … --production`) — where the file is judged on its own: settings read the environment before any file, so as first written the check judged whatever the terminal had exported instead (found by the break-on-purpose run, which exports a database URL of its own). Outside production nothing is refused: a laptop is allowed its defaults.

192. **A hosted Postgres's URL is taken exactly as it is handed out.** Neon's reads `postgresql://…?sslmode=require&channel_binding=require` — libpq's parameters. Two drivers read `DATABASE_URL`: psycopg2 (Alembic), which *is* libpq, and asyncpg (the app), which is not — and SQLAlchemy hands asyncpg every query parameter as a keyword. The old code swapped the driver's name and nothing else: `connect() got an unexpected keyword argument 'sslmode'`, on every request, in an app that had started. Rewriting the URL the way asyncpg wants (`?ssl=require`) broke the other driver: `invalid connection option "ssl"`. So no rewriting is asked of anyone: `app/db/url.py` gives each driver what it reads. For asyncpg `sslmode` becomes `ssl`, `connect_timeout` becomes `timeout`, `options` and `application_name` go into the connection's start-up settings, `channel_binding` is left out (asyncpg has no such switch; the connection is encrypted regardless), and anything else is left out and named in the log rather than passed on to fail. `postgres://` is `postgresql://`. A database is named in a log by host, port and name only.

193. **Nothing prepared is kept from one transaction to the next, so a connection pooler can sit in between.** The address a hosted Postgres recommends is PgBouncer in transaction mode: a server connection is lent for one transaction. asyncpg caches prepared statements, and SQLAlchemy's asyncpg dialect keeps a hundred of its own, each on the server connection it was made on. Through the stand-in's pooler the engine as it was failed on the *second* transaction — `InvalidSQLStatementNameError: prepared statement "__asyncpg_stmt_…__" does not exist` — and the engine as it is answered ten of ten. Both caches are off and every statement that is prepared gets a name of its own. It is not made conditional on the address looking like a pooler's: the cost is a parse per query, and it then works on every address — pooled or direct, and whether or not a pooler tracks prepared statements for its clients (Neon's does; the stand-in's deliberately does not). The pool tests a connection before use and keeps none for more than five minutes: a serverless Postgres sleeps, and its connections die with it.

194. **Migrations run when the container starts — and go to the database's direct address when one is given.** `alembic upgrade head` stays in the image's start command rather than becoming a platform's pre-deploy step: it is idempotent, it works on any Docker host, and a deployment whose migration fails never becomes healthy. `DATABASE_URL_UNPOOLED` is optional; with it, Alembic uses it — a pooler in transaction mode is the wrong road for work that is one long session. On the stand-in the migrations made the `vector` extension and the whole schema on an empty database: migration 001 creates the extension itself, so a new hosted database needs no `init.sql`. Consequence to keep in mind: during a deploy the new instance migrates while the old one still serves, so a migration has to be one the previous version of the code can live with.

195. **The image listens where it is told, is the process that is signalled, and is nobody's root.** Three lines of a Dockerfile that only matter once something else is in charge. `--port ${PORT:-8000}`: a platform names the port it will send traffic to; the old image listened on 8000 regardless, and on the stand-in nothing answered on the port it had been given. `exec uvicorn`: the start command was `sh -c "alembic … && uvicorn …"`, so the shell was process 1 and the server never heard the platform's stop signal — it would have been killed mid-plan after the grace period every time. With `exec` the server takes the shell's place; on the stand-in a stopped instance logged its shutdown, waited for a plan and exited with code 0. And the image runs as an unprivileged user, behind `--proxy-headers` (the platform's proxy says what scheme and client a request really had), with `APP_ENV=production` as its default: an image is something that is deployed, and development overrides it.

196. **What is deployed is exactly what was tested: `constraints.txt`.** `requirements.txt` gives lower bounds, so a fresh install takes the newest of everything. The first image therefore ran SQLAlchemy 2.1.4, sqlmodel 0.0.48, pydantic 2.14 and FastAPI 0.143 where every test here had run on 2.0.51, 0.0.39, 2.13 and 0.141 — and the newer sqlmodel refuses the naive timestamps every model here writes: `Datetime values must have timezone information`. Registering an account answered 500. Nothing local could have shown it; CI's unit tests passed on the new versions, because none of them writes a row. `constraints.txt` is the environment the three suites run on, frozen (112 pins); the image and CI install `-r requirements.txt -c constraints.txt`, and a test fails when a requirement is not pinned or when the environment the tests are running in is not the pinned one. Moving to newer versions is now a decision: upgrade, run the suites, `python scripts/freeze_constraints.py`. The first such move will have to deal with those timestamps.

197. **A platform's health check gets a status it can read: `GET /ready`.** `GET /ping` answers 200 with the errors in its body — the roadmap's rule since Phase 1, and right for a person. A platform reads the status and nothing else: with `/ping` as its health check, the old image's deploy — database unreachable, every request failing — would have been declared healthy and put live. `/ready` says the same in its status: 200 when Postgres and Redis both answer, 503 when one does not. `railway.json` points Railway's check at it. `/ping` is unchanged, except that in production its error text is the kind of error only (`error: OSError`): a connection error's full text names hosts, ports and users, and this address needs no login. The rest is in the log.

198. **Redis is reached over TCP with TLS; a REST address is refused by name.** Roadmap: "Upstash REST API does NOT support pub/sub — must use TCP connection." The live progress of a plan is a subscription (`SUBSCRIBE` on `trip:<id>:events`), and a subscription is a connection that stays open: Upstash's REST API can publish and cannot subscribe. Its Redis also has a TCP endpoint with TLS, `rediss://default:<password>@<name>.upstash.io:6379`, and that URL is all the app needs — the library speaks TLS for `rediss://` and verifies the server's certificate. What the app adds is the mistake made impossible: a `REDIS_URL` that begins `https://` stops a production start with "that is a REST API, and a REST API cannot subscribe… use the rediss:// URL (TCP) of the same database", and so does plain `redis://` to an `upstash.io` host. One leak closed on the way: the tools' cache logged the URL it had connected to as it stood — `rediss://default:<the password>@…`, in every deployment's log. It logs the host.

199. **A hosted Redis closes connections, and that now costs nothing.** Upstash closes idle connections after an hour and all of them when its proxy is redeployed; the library's defaults are no retry and no health check, so each close was one failed request — and for the event stream, which waited on its subscription in one endless read, the end of the stream. Now: a command that finds its connection closed is sent again on a new one (three attempts, a short backoff) — but only that error: a command that *timed out* may have arrived, and a `PUBLISH` sent twice shows the page the same piece of an itinerary twice. An idle connection is pinged before it is used. The event stream waits in pieces through the same retry. And TCP keep-alive probes (after 30 s of silence, 10 s apart, three of them) are how a connection that dies without a word is found. On the stand-in: every ordinary connection killed in Redis, and the next three requests answered 200; the connection under an open event stream killed, and an event published one second later reached the page — the subscription had connected and subscribed again by itself. What is published in the gap is lost (pub/sub has no replay), which is what the page's `GET /status` polling has always been for.

200. **One plan costs a hosted Redis about sixty commands.** Upstash bills, and limits, by the command. Counted on the stand-in around one trip created and planned: 73 — 33 `PUBLISH` (the plan's events; the itinerary arrives in pieces batched by time, not token by token), 17 `GET`, 5 `SET`, a few others, and 13 of connection set-up. On a free plan of 500,000 a month that is several thousand plans. A page left open on a trip costs a `SUBSCRIBE` and then nothing; an idle server sends Redis nothing at all — there is no heartbeat to pay for (#201 is built so as not to need one).

201. **A deploy does not fail the plans that are being made.** #54 left this open: "with several API instances a restart of one would fail runs owned by another". A platform makes that every deploy: the new instance starts while the old one is still serving, and at startup an instance marked every trip it found "planning" as failed — runs cut off by a crash, it assumed. So a run now keeps a sign of life: its note in Redis (the one `GET /status` already read) lives 45 seconds and the run writes it again every 15, for as long as it lasts. A starting instance fails only the trips whose note is gone; one whose note is there is left alone and looked at again every 45 seconds — in case the instance that has it dies after all, which nothing else would ever notice. A note costs a command per 15 s of a run in flight and nothing otherwise. On the stand-in: a second instance started while the first was planning — "1 trip(s) are being planned by another instance — left alone" — and the plan completed; the planning instance killed and restarted — the trip failed 45 s later, with the reason. When Redis cannot be asked, every "planning" trip is taken for dead, as before: a trip stuck for ever is worse than a run failed twice.

202. **A stopping server waits for its plans, and gives up properly the ones it cannot wait for.** A plan takes ten to thirty seconds and is a task of one process. Stopped in the middle, the task is cancelled — and the code that tidies up after a crash did not run for a cancellation, so the trip stayed "planning": every later request a 409, until some instance restarted and repaired it. Now the app waits for its runs when it is told to stop (`SHUTDOWN_GRACE_SECONDS`, 40 by default; `railway.json` gives it 70 before the kill, and a test holds the two together), and a run that is still not done is given up: the page is told (`planning_failed`), the trip is failed — or left completed, if it was a change to a plan that still stands — and the reason is written down for a page loaded later: "The server was restarted while this trip was being planned. Nothing is lost — please start it again." That written reason is also where the run ends, for whoever reads the trip's record afterwards: a run the server stopped under never wrote its closing row, and without an end the next run would have been shown the dead one's searches as its own progress, and its reason if it failed. On the stand-in a server stopped one second into a plan finished it and exited with code 0.

203. **Sentry is on with a DSN, as the roadmap writes it; the error raised on purpose is behind a token.** `sentry_sdk.init(dsn=settings.SENTRY_DSN, traces_sample_rate=0.1)`, plus the environment and the release (the app's version, and the commit when the platform says which). Off without a DSN, and in the test stacks whatever `.env` says. Besides unhandled errors it gets every `logger.error` — which is how a planning run that crashed in the background reaches it, tagged with its `trip_id` and turn, so an error can be found by its trip as a trace can (#175). The roadmap's "deliberately raise an exception on a test endpoint" is `GET /admin/sentry-test?marker=…`: it raises `DeliberateError` and answers 500. It is not open to anyone with an account — every call is an error against the project's quota — but to whoever sends the deployment's `OPS_TOKEN` as `X-Ops-Token`; with no token configured, or the wrong one, it answers 404 like an address that does not exist.

204. **A report is scrubbed before it leaves, by value.** A report is made of whatever was in reach when something failed. Here that is: the login token, in the address of every event stream (`?token=…` — a browser's EventSource cannot send a header); three providers' keys, in the addresses of the tools' own requests, which the SDK notes down as breadcrumbs; the database's and the Redis's passwords, in their URLs; passwords in a login's body; and every secret at once in the repr of the settings object, which is a local variable of the code that starts the app. So the SDK sends no local variables and no request bodies, and everything that is left — every string of every error, breadcrumb and trace — goes through a scrubber that takes out: each secret the process holds, *by value*, wherever it turns up; whatever an address carries under a name like `token`, `key`, `apikey`, `appid`, `password`; credentials inside a URL (the host stays: which database is worth knowing); bearer tokens and JWTs; e-mail addresses; and any value kept under a name like `authorization` or `x-ops-token`. A report that cannot be scrubbed is not sent. On the stand-in everything the backend had sent — 201,593 characters over a registration, a plan and a deliberate error — was searched for thirteen secret values: none. The same reasoning took the token out of the server's own access log, which wrote every stream's address in full.

205. **Nothing answered may be cached, and a 500 says nothing of itself.** In production the frontend's host proxies `/api/*` to this server, and Vercel's changelog says its CDN respects `Cache-Control` from external origins by default. Every answer here is one traveller's, behind their token; the origin now says `Cache-Control: no-store` on every answer that did not say otherwise, so it does not depend on how any proxy is configured. (A plain ASGI wrapper: the usual middleware base class wraps the response body, and the event stream must not be wrapped.) And an error nobody caught is answered in the envelope every other error has, with a message that tells the traveller nothing of what went wrong — the error itself is raised on, into the log and into Sentry.

206. **No function is in the path of a plan, so there is none to time out.** Roadmap: "check function timeout — planning takes 15–30s, default 10s will fail. Use streaming or upgrade timeout." Neither was needed, because of how the app has worked since Phase 13, and it is worth saying why. `POST /plan` answers 202 at once (20 ms through the frontend on the stand-in) and the plan is made in the background. Its progress is an event stream that the browser opens *straight to the backend* — it never passes through the frontend's host. Everything else goes through `/api/*` on the frontend's origin, which on Vercel is a rewrite carried out by its proxy, not by a function: the proxy waits 120 seconds for the backend to begin to answer, and the slowest such request measured was the PDF export at 0.4 s. What can go wrong is configuration, and both ways are closed: the two addresses the frontend needs (`BACKEND_URL`, `NEXT_PUBLIC_API_URL`) are compiled in when it is built, so a deployment build without them now stops with their names instead of producing a site that proxies to its own localhost; and the browser will only read the stream if the backend names the site in `CORS_ORIGINS` — a production start without a deployed origin there is refused (#191). `CORS_ORIGIN_REGEX` lets in a host that gives every deployment an address of its own. That last rule fixes the order of a first deploy: the backend's address, then the frontend built with it, then the backend started with the frontend's.

207. **A production-like stack, and what it does and does not prove.** As with LangSmith (#179), the acceptance names services this build had no account on, and the same answer was given: reproduce exactly what makes each one different from a laptop, and be exact about the rest. `docker/prodlike` is the deployed image, started the way a platform starts it (environment only, a port to listen on, a stop signal), against a Postgres that refuses a connection without TLS and starts empty, PgBouncer in transaction mode that wipes each server connection after every transaction, and a Redis that only speaks TLS, wants a password and closes idle connections; `scripts/sentry_receiver.py` receives the SDK's reports over HTTP and shows what they contain. `scripts/prod_check.py` asks a running deployment the roadmap's questions from outside — the backend answers, pgvector is there, a message published over TCP arrives at a subscriber, the deliberate error is reported, the frontend's `/api/*` reaches the backend uncached, a trip is planned end to end with its stream read as a browser reads it — and `e2e-production/` plans one in a real browser. On the stand-in: 29 of 29, and the browser check passes. Both take the real addresses unchanged. What this does **not** prove is anything about the five services themselves: that Railway builds this Dockerfile and honours `railway.json`, that Neon's pooler and its `channel_binding` behave as the stand-in's Postgres does, how Upstash's proxy really drops a connection, that Vercel's proxy is as its documentation says, that Sentry accepts the DSN and groups the event. LangSmith's lesson (#189) is that the first real run finds what no stand-in can. That run is five sign-ups away, and its steps are in `HOW_TO_RUN.md`, Step 25.

## Phase 28 — CI/CD Pipeline

> Build log: `docs/phase28_build_log.md`. Two things to know before the entries. The repository is **private**, and that decides more than it seems: its Actions results cannot be read from outside without a login, every job is billed in whole minutes of a monthly allowance, and — on GitHub's free plan — a branch cannot be protected, so "a broken test blocks the merge" is something GitHub will show and not enforce (#211). And the deploy half has nowhere to deploy to yet (Phase 27's accounts): it is built to say so and pass until it has (#213). Every workflow was run, on the files as they are, by a local runner (`act`); what only GitHub can show is listed in the build log.

208. **Two jobs on every push, side by side — not five.** Roadmap: "on every push — `ruff check src/`, `pytest tests/unit/ tests/contract/ -v`", an `alembic check` step, "lint + tests in under 3 minutes". The natural shape is a job each for lint, migrations, tests, the frontend, and a gate. In a private repository each job is rounded up to a whole minute of a 2,000-minute month, and each pays for its own checkout and install: five jobs cost about eight minutes a push. So the backend's three checks share one job — lint first, because it is the cheapest way to fail; then the migrations; then the tests — and the frontend has the other. Two checks to look at, two to require, about five billed minutes a push; side by side they finish in the time of the slower one.

209. **Only pushes start CI; a pull request is not listened for.** The workflow used to start on `push` to any branch *and* on `pull_request`, so every commit on a branch with an open pull request ran twice — and left two checks of the same name on one commit. Worse than waste: a required check is satisfied by a check that was *skipped*, so two checks of one name where one may be skipped is a way for a failing commit to look mergeable. A pull request's commits are pushed commits, and are checked as that. What is given up is the test of the merge *result* rather than of the branch's head, which "require branches to be up to date" covers where a branch can be protected.

210. **The migrations are run, compared, taken down and put up again — against a real Postgres.** Roadmap: "`alembic check` step: fails the build if DB schema is ahead of migrations." `alembic check` compares the models with a database, so the job has one: a `pgvector/pgvector:pg16` service, because the first migration creates the extension. Four commands: `upgrade head` (every migration applies to an empty database — what a first deploy does), `check` (the models say nothing the migrations do not), `downgrade base` and `upgrade head` again (each migration can be taken back: Phase 26's lesson, where a downgrade that left a column behind poisoned a database for every run after it). A model given a column and no migration fails the job at `check` with "New upgrade operations detected".

211. **CI says a commit is broken; whether that stops a merge is a repository setting — and on this repository's plan it cannot be switched on.** Roadmap: "A deliberately broken test in a PR must fail the pipeline and block merge." The first half is the pipeline's and is shown: a test that asserts 1 + 1 == 3 fails the `backend` job, and with it the commit's check. The second half is branch protection — `main` requires the checks `backend` and `frontend` before a merge — and GitHub's plans page lists protected branches for private repositories under Pro, not Free. On a free private repository the pull request shows the red cross and the merge button still works. Three ways out, the user's to choose: make the repository public, take the paid plan, or merge by looking. What the pipeline does regardless is the part that matters most downstream: a commit that fails on `main` is not deployed (#212).

212. **The deploy is the last job of the same run, and only after both checks.** Roadmap: "CD on merge to main: GitHub Actions → `railway up`". On `main` the CI run has a third job that `needs` the other two: a commit that fails a test, the linter, a migration or the build is never deployed, whatever let it onto `main`. The deploy itself is a workflow of its own (`deploy.yml`) that CI calls — so that it can also be started by hand, to deploy `main` again — and deploys are never cancelled half-way and never overlap: a second waits for the first.

213. **A repository with nowhere to deploy to can still merge.** Until the accounts exist, every merge to `main` reaches the deploy job with no token. Failing there would turn every merge red for a reason nobody can act on; going through the motions with an empty token would be worse. So the job's first step asks whether there is a target — the secret `RAILWAY_TOKEN` and the variable `RAILWAY_SERVICE` — and without one says "Nothing was deployed" as a notice on the run and passes; every later step runs only when there is one. The day the two are set, the same merge deploys, with no change to the repository.

214. **"Deployed" is not "live": the pipeline waits until the public address answers with the merged commit, and says how long that took.** Roadmap: "verify via `railway status`"; "automatic Railway + Vercel deploy within 5 minutes". `railway status` is run, and says what Railway believes. What a traveller gets is something else, so the deployment is asked: the pipeline sets `GIT_COMMIT_SHA` on the service before `railway up`, the backend answers `GET /version` with it, and the site — which Vercel builds by its own GitHub integration, not from this workflow — is compiled knowing its commit and answers the same at its own `/version`. `scripts/wait_for_release.py` asks the backend, the site, and the site's `/api/version` (the site reaches a backend that is running it too) until all three say the merged commit; then it writes the time from the merge to that moment on the run's page. Past five minutes is a warning, not a failure: a deploy that is live is live. Not live in ten is a failed run, with what each address last answered.

215. **The site is not deployed from here, and is not held back by the checks.** "Vercel auto-deploy via GitHub integration" is a setting in Vercel (import the repository, Root Directory `src/frontend`): Vercel builds every push to `main` itself, the moment it is pushed. The backend's deploy waits for the checks; the site's does not. For a few minutes after a merge the new site talks to the old backend, so a change to the API that the old backend cannot serve has to go out in two steps — the same rule Phase 27 found for migrations (#194).

216. **Every night at 02:00 UTC: the tests that need real services, and one comment that says how it went.** Roadmap: "`RUN_INTEGRATION=1 pytest tests/integration/ -v` + eval suite from Phase 33 + posts summary to a dedicated GitHub issue via `gh issue comment`." The job has a Postgres with pgvector and a Redis as services and runs the integration suite on them; the eval suite's step is there and runs once `tests/eval/` exists. The comment goes on the open issue labelled `nightly` — made the first night, with the label — so the nights are one thread, read from the top and muted by whoever does not want a notification a day. A schedule only ever runs the workflow that is on `main`, so a change to the job could not be tried before it was merged; a push to a branch named `nightly-check/…` runs it too.

217. **A night with no report is a failed night.** The comment is written from the tests' JUnit reports, and the obvious way to write it has a hole: when the tests crash before the first one runs — an import error, a database that never came up — there is no report, so there are no failures in it, and the night reads as perfect. The integration suite is therefore *required*: no report is "DID NOT RUN", a failure. A suite that fails does not stop the night either — the comment is posted whatever happened, and only then is the run failed, so that a bad night is both a red run and a comment that says which test and why. Seen in the local runner by accident before it was seen on purpose: its first night could not log in to its database, and the summary, the post and the red run all happened as written.

218. **What a workflow does is a script, and a script is tested.** A workflow file can only be run by pushing it; logic inside it is logic nobody runs until it matters. So the three pieces with any decisions in them are programs in `scripts/` — the wait for a deploy, the night's summary, the posting of it — with tests of their own; the last runs against a stand-in for GitHub's CLI that writes down what it was asked. The workflow files themselves are read by tests that hold what each must do and must never do: which events start it, which commands run and in what order, that every step of a deploy is behind "is there a target", that the comment is posted before the run is failed, that only GitHub's own actions are used, each at a named version, that no workflow may write to the repository, that every job has a time limit. Three findings came from running the pieces as GitHub and as a Mac would: the posting script did not parse on macOS's bash 3.2 (an apostrophe inside `${…}`); the wait could not be handed a clock, so its test waited ten real minutes on an address that did not exist; and the night's summary step, run with the `bash -e` GitHub uses, stopped at the summary's own exit code on a bad night — before putting the summary on the run's page.

219. **Run for real, by a local runner — and what that does and does not show.** GitHub's own results could not be read: the repository is private and this build has no GitHub login beyond git's. So every job was run by `act`, which executes the workflow files as they are, in containers, with the service containers they ask for: the backend job (lint, the migrations up, checked, down and up, 1,010 tests), the frontend job (types, lint, a production build), the nightly job (60 integration tests on a real Postgres and Redis, the summary, the post — to the stand-in), the deploy job with no target. And broken on purpose, on copies: a failing test, a lint violation, a model with no migration, a type error — each failing the step it should — a failing test on `main`, where the deploy must not run — and two bad nights: one with a failing test, one whose tests never started. Both were summarised, posted and failed. Two things `act` did that GitHub does not, both worth knowing: it loads the repository's `.env` into every job unless told otherwise — which hid the nightly job's own database settings behind the laptop's, and put the laptop's keys into the runner — and it leaves a service container holding its port if the next run starts too soon. What it cannot show: GitHub's runners' real speed, the cache, the token's permission to write an issue, a schedule firing, and the deploy with a target.

220. **One deployer.** Phase 27's steps connect the Railway service to the repository, and a connected service deploys every push to `main` by itself — at once, before any check. With the pipeline deploying too, a merge would be deployed twice, and the first time untested. Railway has an answer of its own, "Wait for CI": it holds its deploy until the commit's GitHub Actions have finished. That would do the first half of this phase with no token at all — and cannot be combined with the second: the run's last job waits until the merged commit is live, and Railway would be waiting for that run. The roadmap asks for `railway up` from the pipeline, and the pipeline is where the wait and its timing can be written down; so the service's own automatic deployments are switched off (`HOW_TO_RUN.md`, Step 26) and the pipeline is the only thing that deploys the backend.

## Phase 29 — Observability: Prometheus, Grafana & OpenTelemetry

Built and verified on this machine — the production-like stack of Phase 27 with Prometheus, Grafana, Jaeger, Loki and Alloy beside it (`scripts/observability.py`, `scripts/observability_check.py`). Not on a deployment: there is none yet (#207). `docs/phase29_build_log.md`.

221. **Three signals, one way of saying whose the work is.** Metrics answer "how much, how often, how slow"; a trace answers "what did this one request do, in what order"; log lines answer "what did the code say while it did it". They are only one system if the same id finds all three, so the id is set in one place and read by everything: two context variables, `trip_id` and `user_id` (`src/telemetry/context.py`), set by a middleware as a request comes in — the trip from the address (`/trips/<id>/…`), the user from the login token (the header, or `?token=` for an event stream). A filter on the one log handler puts them on every line; a span processor puts them on every span, as `trip.id` and `user.id`, whoever made the span. Nothing that logs or queries has to know. Context variables rather than arguments passed down, because a task starts with a copy of its starter's context: the planning run that outlives its request, and the cache warming POST /trips leaves behind, know whose they are without being told. Two places have to say it themselves: POST /trips (there is no trip in the address — there was none yet), and the tool server, which is another process (#231).

222. **`src/telemetry/`, used by two processes and importing neither.** The API server and the tool server it starts both log, and both make spans; the tool server is deliberately free of the app's imports (Phase 3). So the package takes settings as an argument and knows neither. It is not `src/ai/tracing.py`: that one (Phase 26) uploads what the planner *thought* — prompts, replies, the state between steps — to LangSmith, for whoever tunes the planner. This one records what the system *did* — requests, statements, commands, calls, and how long each took — for whoever operates it. A plan is both, and each has its own switch.

223. **`GET /metrics`: open where the app is developed, the operations token where it is deployed.** The numbers name every route and say how busy each is: not worth much to an attacker, and not for the whole internet. With `OPS_TOKEN` set (Phase 27 made one for the deployment) they are for whoever sends it — as `Authorization: Bearer …`, which is what a Prometheus scrape config can send, or as `X-Ops-Token` like the other operator's route. With none set they are open in development and *closed* in production: a deployment that forgot the token does not publish its metrics. A caller who may not read them gets what a route that is not there gives (404). The route is not in the API's schema, is not itself counted, and is not traced.

224. **Requests are counted by the roadmap's library, not by its one-liner.** `Instrumentator().instrument(app).expose(app)` works for one app in one process. Its middleware makes its metrics as it is built, and a metric can be registered once: a second app object in the same process failed on its first request with `DuplicateTimeseries` — which is the test suite's situation exactly (`app.main` and `src.backend.app.main` are the same file under two names; 47 tests failed). So the library's metrics are made once and every app's middleware is handed them; the route is still the library's `expose`. Three settings matter: endpoints are named as the router names them (`/trips/{trip_id}/plan` — an id in a label is a series per trip, for ever); a request's duration is the time to its first byte, because an event stream is open for minutes by design and those minutes are not latency (4 s open, counted as 5 ms); and requests in progress are counted, which is how open event streams can be seen.

225. **`llm_calls_total{agent, model, status}` is counted where every model call already passes.** Phase 26 attached one LangChain callback handler to every model call in the process, to count tokens. The same handler counts the call. *Agent* is the name of the meter open where the model was asked — `timed_run("flight_agent")`, which every agent already opened around its work and now names, with the name its `agent_runs` row is logged under; a call made in nobody's work is `unmetered`. *Model* is the one that was asked for, not the one that answered: a provider answers under a dated name of its own, and a call that failed has no answer to read a name from — the label would differ between a model's successes and its failures. *Status* is not in the roadmap's list for this phase and is in Phase 34's alert (`llm_calls_total{status="error"}`): a label added later is a new set of series, so it is there now. The tokens and their list price are counted beside it (`llm_tokens_total`, `llm_cost_usd_total`): the handler has them in its hand.

226. **`mcp_cache_hit_ratio` is counted in one process and exposed by another.** The cache is the tool server's; `/metrics` is the API server's. Four ways across were weighed. A second `/metrics` port on the tool server: a deployment has one public port. prometheus-client's multi-process mode: a directory of memory-mapped files shared between two different programs, to be wiped at every start — for one gauge. Counters kept in Redis: a command per lookup on a Redis that bills by the command (#205), and no numbers at all when Redis is the thing that is down. What was built: the tool server tallies the lookups made for each call — hit, miss, or *error* when Redis could not be asked — and sends the tally to its caller with the answer, as one of the protocol's own log messages; the caller counts (`mcp_cache_lookups_total{cache, result}`). An error counts against the ratio: Redis gone is every lookup failing, and the ratio has to fall. The gauge itself is hits ÷ lookups over the last five minutes, not since the process started — after a good week a bad hour would barely move it — and NaN when there was no lookup: "nobody asked" is not "nothing was found", and an alert on a low ratio must not fire at night. The counter is what a dashboard should use; the gauge is there because the roadmap, and Phase 34's alert, name it.

227. **`itinerary_builds_total{status}`: a build is counted by its fate, where the fate is decided.** *retry*: the evaluator sent it back and it is being built again (`retry_dispatch_node`). *failure*: the loop ran out of tries (`builder_failed_node`). *success*: it was saved — counted after the commit, not before: a build that passed and could not be written is not a plan anybody has. The three add up to the number of builds. A run that never got as far as building (nothing found; a budget conflict handed back) is not a build: that is the run's outcome (#228).

228. **A planning run is timed by itself.** `POST /trips/{id}/plan` answers 202 in milliseconds and the plan is made by a task it leaves behind, so the request's duration says nothing about how long a plan takes — and an alert on it (Phase 34: "p99 for POST /plan exceeds 30 s") could never fire. `planning_run_duration_seconds{kind, outcome}` times the run: *kind* is what started it (plan, replan, refine, retry), *outcome* how it ended (completed, no_plan, crashed, interrupted), with `planning_runs_in_progress` beside it. For Phase 34: the alert belongs on this histogram.

229. **A series that can be listed exists at zero before anything happens.** Found by the first run of the check: after the first plan the "Planning runs" panel was empty, and a request rate could be asked for one endpoint of ten. A counter exists from its first increment, and Prometheus cannot see a rise from "not there" to 1 — `rate()` and `increase()` count from the second. On a busy system that is one event; on a quiet one it is the first plan after every restart missing from its chart, and the first error missing from its alert. So every series whose labels can be enumerated is made at zero at import: build statuses, run kinds × outcomes, tools × status, caches × result, and — from a list of who asks which model (`ASKED_BY` in `src/ai/llm.py`, held to the truth by a test that plans a trip and looks at who asked) — every agent's calls, errors, tokens and cost. What cannot be listed is the library's own `http_requests_total`: an endpoint's first request is not in its rate.

230. **One trace from the request to the row.** The request, every SQL statement and every Redis command are spans made by OpenTelemetry's own instrumentation of FastAPI, SQLAlchemy and redis-py — the roadmap's two packages and a third for Redis, which it names in the acceptance. Between them the app makes its own: `planning run`, one span per `agent_runs` row under the row's own name (`timed_run("flight_agent")` again), `llm <model>` per model call, `mcp.call <tool>` per tool call, `provider <name>` per request to a provider. The run is the request's child although it outlives it by seconds: it began inside the request, and a span's parent is whatever was under way when it began. So one plan is one tree — some 106 spans on the production-like stack — from `POST /trips/{trip_id}/plan` down to `INSERT INTO itineraries`. An engine is instrumented by instrumenting the *making* of engines, so `make_engine` asks the module for `create_async_engine` when it is called; an integration test makes a second engine and looks for its span.

231. **A trace crosses to the tool server in the call's `_meta`.** A span is its parent's child because the parent is in a context variable — which a process boundary ends. The MCP protocol gives every request a `_meta` object for exactly this; the caller puts three things in it: `traceparent` (W3C), `trip_id`, `user_id`. The tool server starts its span as the child of the one that was sent and sets the two context variables for as long as it answers; the tools run in worker threads that start with a copy of that context, so the cache's Redis commands and the requests to providers are that span's children and the server's log lines carry the caller's trip. A caller that sends nothing (the MCP Inspector) gets the same answers and a trace of its own. One thing had to be undone: the session to the tool server is made by whichever request needs it first, and its reader tasks live as long as the process — made in that request's context, they would log under that trip, as part of that trace, for every request after it. The session is made in nobody's context.

232. **Health checks are not traced — by a sampler, not an exclusion list.** A platform asks `/ready` every few seconds and Prometheus `/metrics` every five; as traces they would be most of the store. Excluding their addresses from the request instrumentation is not enough: the `SELECT 1` and the `PING` behind `/ready` would then be traces of their own, one span each. A sampler that passes over those requests passes over everything under them (`ParentBased`). For the same reason startup's queries are under one `startup` span. Two other things would have flooded a trace: an event stream's `send` per event (the instrumentation's receive/send spans are off), and the pieces of the itinerary published while the model writes — twenty Redis commands a second that say nothing each — which are published and not recorded.

233. **Nothing leaves as it was recorded.** The instrumentation writes down what it sees: a request's whole address — and an event stream's ends in `?token=<the login token>` — the address it came from, and, on an error, the message and the stack trace, which for a failed call to a provider include the address that was called, key and all. So every span is put through Phase 27's scrubber before it is exported (`traces.Scrubbed`: attributes, error events, status), and a request's span leaves without the client's address — whose it was is `user.id`. A span that cannot be scrubbed is not sent. The JSON log lines get the same: message and traceback scrubbed, and the access line written without the address it came from. Two libraries are left to their defaults because their defaults are right: SQL is recorded as its statement, never its values; a Redis command as its name, never its arguments. One is not used at all: httpx's instrumentation records the address of every outgoing request, and two providers take their key in the address — a request to a provider is a span made by hand, with the provider's name, the status and the number of attempts.

234. **Log lines: JSON where they are stored, text where they are read.** `LOG_FORMAT=json` (the default where `APP_ENV` is production) makes every line the process logs — the app's, the web server's, a library's — one JSON object: timestamp, level, logger, message, service, `trip_id`, `user_id`, `trace_id`, `span_id`. The two ids are on every line, `null` where the work is nobody's: a field that is sometimes missing is harder to search than one that is sometimes empty. It is set up as the app's module is loaded, not at startup, because the web server's first lines come before startup and a log store should not have to cope with two kinds of line; Python's own warnings are taken into the log for the same reason. Libraries are heard from WARNING up — at INFO an HTTP client logs every address it calls — and an answered health check is not a line. `text` leaves the console exactly as it was. The tool server logs the same way under its own `service`, to standard error: its standard output is the protocol.

235. **The lines get to Loki by Alloy, and the ids are not labels.** The app writes to its output and knows nothing of where lines go (in production that is the platform's log store — Railway's reads JSON and searches by attribute). Here Alloy reads the app's containers through Docker, and `./logs/*.log` for a backend run on the host, and sends them to Loki. Promtail, the usual name here, reached its end of life in March 2026. `service` and `level` become labels: a handful of values, what a stream is selected by. `trip_id`, `user_id` and `trace_id` become structured metadata: a value per trip is a stream per trip if it is a label, which is what brings a log store down — and as metadata they are searched without parsing the line: `{job="tripplanner"} | trip_id="…"`.

236. **Jaeger, and not through Grafana.** The roadmap says Jaeger or Zipkin; Jaeger 2 takes OTLP directly, so there is no collector in between. Grafana has a Jaeger data source and it is not set up: it asks Jaeger for routes (`/api/services`, `/api/traces?service=…`) that Jaeger 2.22 no longer serves — its health check answers "404 Not Found" — and a data source that half works is worse than a link. A log line's `trace_id` is a link to that trace in Jaeger's own UI, and the check script speaks Jaeger's `/api/v3`.

237. **The dashboard leads with six numbers and uses a table where there are twenty of something.** One row of tiles (requests, errors, p95, plans being made, cache hit ratio, model calls), then rate / errors / duration per endpoint as three charts *and* a table — one row an endpoint, because twenty lines in twenty colours cannot be read and a table can. One scale per chart, never two. Colour means something only where there is something to mean: completed / success green, retry / no plan amber, crashed / failed red — and no other series is drawn in those. "No request failed" is 0 %, not "no data" (`or vector(0)`); a ratio of nothing is "no lookups", not a number. Legends are sorted busiest first. The file is in the repository and is what Grafana shows; a test holds every metric a panel asks for to the ones the app exports, so a renamed metric fails a test and not, silently, a panel.

238. **Off is off.** Tracing is on only with `OTEL_EXPORTER_OTLP_ENDPOINT`, and never where `APP_ENV` is test; without it nothing is recorded and nothing is sent — to the tool server either: a call carries a `traceparent` only when there is a trace. The suites set their own logging and tracing whatever `.env` says, so a developer with a trace endpoint in `.env` does not find a few thousand test requests in Jaeger. And because a process may set its tracer provider once while what listens to it changes (nobody, the exporter, a list a test reads), "nobody listening" is checked by the sampler: spans made then are not recorded, a log line is given no trace id to point at, and — found by a test that passed alone and failed after another — nothing is sent along with a tool call.

239. **Verified on the production-like stack; what that does and does not show.** `scripts/observability_check.py --prodlike` plans a real trip on the deployed image (TLS-only Postgres behind a pooler, TLS-only Redis, real providers and models) and asks the four programs what they saw: 45 expectations, among them one trace of some 106 spans across both processes with no span missing its parent, the trip's log lines from both services found by its id, and the metrics behind the operations token. What it does not show: a deployment — where the trace backend is somebody's service reached over the internet (the settings are the same: an address and a header), where the platform, not Alloy, collects the lines, and where Prometheus has to be somewhere that can reach the backend. None of that exists yet. And nothing here alerts: that is Phase 34.

## Phase 30 — Load Testing & Performance Baseline

Measured on one laptop that ran both the load generator and the system under load: the image that is deployed, on the production-like stack of Phase 27, with stand-ins for the models and the providers. Not on a deployment: there is none yet (#207). `docs/load-test-report.md`, `docs/phase30_build_log.md`.

240. **The stand-ins are a different program, not a switch.** A planning request asks three models and five providers, and none can take load: Gemini's free tier is about twenty requests a day, Groq allows one plan's tokens every few seconds, the flight and hotel providers are sandboxes. So a load test needs stand-ins — and the image under test must still be the image that is deployed. The usual answer, an environment variable that puts the app into a "stub mode", is the one thing ruled out: a flag is set by accident, and a production that plans trips from made-up flights looks healthy. What was built has no flag. The stand-ins live in `loadtest/standins/`, outside `src/`; the deployed image copies `src/`, the migrations and nothing else, so the code is not there to be switched on. The load test's image is that image with the one directory added (`docker/loadtest/Dockerfile`, `FROM` the deployed one) and a different thing to serve — `uvicorn loadtest.standins.app:app`, the deployed command word for word but for that. And for the one accident those two leave — somebody hands the load test's image a deployment's settings — that module refuses to load unless the database and the Redis are on this machine: a host with a dot in its name is somewhere else (`guard.py`). The stack is given placeholder keys and is never shown the repository's `.env`. A test holds each of the four.

241. **What is stood in for is the far side of each call, and nothing nearer.** Three seams. The model *classes* the planner instantiates (`ChatGroq`, `ChatGoogleGenerativeAI`): a stand-in answers through LangChain, so the callback that meters tokens, counts `llm_calls_total` and makes the span still runs — replacing the functions that call a model (what the test suite's `network_stubs` does) would have skipped all of it. The one function behind the embedding API. And, in the tool server's own process, the tools' `httpx.get` / `httpx.post`: the tools still validate, look in their Redis cache, hold one search per key, wait for their rate limit and retry — only the request itself is answered, in each provider's own shape. The tool server is started through `loadtest/standins/tool_server.py`, which puts those in and then runs the real server module. So what a load test loads is the app, Postgres through its pooler, Redis, and the tool server as a process with its threads. The stand-in's plan has to pass the real builder's checks and the real evaluator's, for every destination the test uses: a test does that too.

242. **A stand-in takes as long as the real thing.** A fake that answers at once moves the bottleneck to wherever the fakes are not, and a load test of it measures the fakes. Each stand-in waits between the fastest and the slowest the real one was seen to take, most often near the usual: intent parsing 1.8–4.6 s, local tips 1.0–2.6 s, the itinerary 5.0–8.4 s (its last 1.6 s arriving in pieces at the 1,460 characters a second a model was measured writing), an embedding 0.8–3.3 s, a flight search 3.4–7.0 s, hotels 5.5–7.5 s — from Phase 29's traces and one more real plan made for this phase (`loadtest/standins/timing.py` has the table). A provider is waited for on the worker thread that asked, as a blocking request holds it. Checked by making the same plan both ways: 12.6 s real, 11.5 s stand-in, the same steps and events in the same order. What the stand-ins leave out, and the report says: the CPU of talking to a provider (TLS, an HTTP client, a JSON document per token), a Gemini that does not answer for 15 s, and a provider's own 429.

243. **k6 cannot read an event stream; a k6 built with `xk6-sse` can.** Tried first, as the brief said to: `http.get` on `GET /trips/{id}/stream` waits for a response that never ends and reports a request timeout — it can neither react to `planning_complete` nor measure anything. The `xk6-sse` extension reads the stream. Its README says k6 now resolves it by itself on `import`; k6's build service answers "unknown dependency: k6/x/sse" (it builds the official extensions only, and the registry's listed versions of this one are for k6 v1). So the binary is built: k6 v2.3.0 with `xk6-sse` v0.2.0, by the `grafana/xk6` image, all three pinned (`python scripts/loadtest.py k6`; no Go, no Homebrew — Docker). Three things about it shaped the script, each found on a toy stream before the app was touched: no timer fires while a stream is open, so the page's "ask `/status` every 3 s" is asked in bursts when an event arrives; the event's name keeps the `\r` of this server's line endings; and the extension reports a stream's whole life as `http_req_duration` — untagged, the p99 of "request latency" would have been how long a page stays open.

244. **Visits start at a fixed rate; a visit is what the trip page does.** An open model (`constant-arrival-rate`): a fixed number of virtual users each waiting for its answer slows down with the server, and so reports a slow server as a quiet one. One visit is the requests `src/frontend` makes for someone who comes to plan a trip — sign in (half the visits: a login lasts a day), the trips list, create, the trip's page (`/trips/{id}`, `/status`), its event stream opened with `?token=` as an `EventSource` must, a few seconds of the traveller writing, `POST /plan`, `/status` every 3 s while it runs, then `/itinerary`, `/trips/{id}`, `/status`, `/similar`, and the page left open while it is read. The roadmap's four endpoints, and the six the page asks around them; a test holds every one to the app's own routes. Not in the mix: refinements, the PDF, search. Twelve destinations and two sets of dates — 24 different flight searches, because the app's own limiter keeps to the flight provider's 30 a minute and a test that asked for more distinct flights than that would be measuring the provider's limit.

245. **A plan's duration is its own metric, and "holds" is defined before anything is measured.** `POST /plan` answers 202 in milliseconds; `plan_duration` is from that request to `planning_complete` on the stream — what `planning_run_duration_seconds` is on the server's side (#228). A rate *holds* when at least 99 % of the visits get their plan, a plan takes under 30 s at p95, requests that are not streams take under 1 s at p99, and fewer than 1 % of them fail (`scripts/loadtest.py`). Written down first so that "it coped" cannot be decided after seeing the numbers.

246. **One request in ten is traced while the load runs.** The default is every request (`OTEL_TRACES_SAMPLE_RATIO=1`), which is right for a system nobody is loading. Under load on one machine the trace store is part of the machine: at two visits a second, every request traced is some 250 spans a second into a Jaeger that keeps them in memory, inside the same 8 GB the database and the backend have — an observer that a deployment's trace backend, being elsewhere, would not be. A tenth still leaves a dozen whole traces of plans a minute to find a slow one by. The same ratio before and after the change; a request that is passed over costs the app a sampling decision and nothing else.

247. **The runner looks at the stack while k6 loads it, and keeps what it saw.** k6 knows what a traveller saw; why is on the other side. Every two seconds `scripts/loadtest.py` asks the pooler (`SHOW POOLS`: clients being served, clients waiting — which needed the pooler told that the stack's user may ask, `stats_users`), Postgres (`pg_stat_activity`: connections idle inside a transaction), the backend's own `/metrics`, and Docker (each container's memory against the 8 GB). A run is one file, `docs/loadtest/<name>/rate-<r>.json`: k6's figures, the stack's, a time series of both, and whether the rate held. The report's tables are printed from those files, not typed.

248. **A run the machine slept through is not kept.** Found by the first smoke run having a 34-second hole in it: the laptop's lid was closed, on battery, and macOS was asleep for some four seconds in every nine while every program appeared to run. A stand-in's 6.5-second wait was logged 41 seconds after it began; k6's plan durations were four seconds longer than the server's own. Nothing looked wrong. The wall clock runs on while a machine sleeps and the monotonic clock stops, so the two drift apart by exactly the time asleep: the runner compares them across a run and refuses to keep one that drifted by a second (`Awake`). `caffeinate` is asked for too, and does not help with a closed lid.

249. **Three numbers added before the baseline: how near the process is to running out.** `db_pool_connections{state}` and its limit, `redis_pool_connections{state}` and its limit, `event_loop_lag_seconds`. They change nothing about what the app can do — instrumentation is not tuning — and without them "the pool ran out" would have been an inference from request latencies. Read from the libraries' pools at scrape time, never failing a scrape; a row of the dashboard shows each against its limit. They are per process, like every metric here (#226): if the app is ever run as several worker processes, these three need the same answer the rest do.

250. **The baseline is the stack as Phase 29 left it, and it holds one visit every ten seconds.** Four rates, 180 s each: at 0.1 visits a second every plan arrives in 11–13 s and requests take 9 / 21 / 210 ms (p50 / p95 / p99) — 1.3 requests a second. At 0.2 the request p99 is 1.3 s; at 0.4 a plan takes 25 s and every request a second; at 0.8, 51 of 145 visits get a plan, a plan takes two minutes, the p99 is 15.8 s. Not one request failed and the server finished every plan it was asked for: it was only ever waiting. The backend never used a sixth of one core. Kept as measured (`docs/loadtest/baseline/`), before any setting or line was changed — a baseline taken after "one obvious fix" is not one.

251. **The guess this phase began with was wrong about where, and is kept in the report.** *The pool runs out at around 15 concurrent plans* (recorded as a guess before anything ran). The app's pool of 15 does fill — at 0.4 visits a second, where a healthy system has five plans in flight. The wall is the pooler's four server connections, reached at four plans; the sixteen plans that then fill the pool of 15 are there because they are already queueing. Right about the kind of limit, wrong about which pool and by a factor of four about when. The report says so under its own heading: a wrong hypothesis that was tested is a result, and the next reader's guess will be the same one.

252. **The configuration change: the pooler lends 90 connections, and the app's pool is a setting — 40 here.** The hypothesis was written first (00:51, the settings changed at 00:52): *the number of plans the stack can make at once is the number of connections it can hold open, because every plan in flight holds one idle inside a transaction — some 14 connection-seconds a plan, so 4 ÷ 14 ≈ 0.3 plans a second.* If so, connections alone move the wall by their own factor, and nothing else needs touching to find out. They did: 1.6 visits a second, 20.8 requests a second at 199 ms p99, every plan in under 14 s — sixteen times the baseline — with the connections in use following the plans in flight one for one. **Why 90:** it is what the pooler this one stands in for lends (Neon's PgBouncer: 90 % of `max_connections`, 104 on its smallest compute); the 4 was Phase 27's, for a stack that planned one trip at a time, and it made the wall come earlier here than a deployment's would — there the app's own 15 would have been first. **Why 40** (`DB_POOL_SIZE=10`, `DB_MAX_OVERFLOW=30`): two instances are alive at once during a deploy and both must fit in the pooler; a test holds that sum. The defaults stay SQLAlchemy's 5 + 10 — someone who sets nothing gets the app they had.

253. **The cause was in the code: a transaction left open while a model is asked.** More connections moved the wall and left its cause: 30 of 40 connections idle inside a transaction at 1.6 visits a second, and connections are what a hosted Postgres has fewest of. Every step of a run ends in `log_agent_run`, which committed its row and then refreshed it; the refresh is a `SELECT`, a `SELECT` begins a transaction, and nothing ended it until the next step's commit — after the model had answered. The refresh is gone (every column of the row is set in the code; nothing read what it fetched) — and so is the open transaction of the function's *other* read, the two sums of the cost alert (#184, Phase 26), added up after every step that asked a model: it is ended before the function returns. That second read was the larger half, and it was found by breaking the fix on purpose: with the read-back alone restored the baseline's pools still carry 0.8 visits a second (a plan then holds a connection for a second and a half, while the local tips are asked for); with the function as it was they do not — 118 of 145 plans, the pool at 15 of 15, eleven waiting at the pooler. The step logged before the itinerary's six seconds is one that asked a model. The rule it leaves — *a read's transaction is ended before something outside is waited for* — is applied at the other four places that broke it: the preference extractor and `POST /refine` (a lookup, then a model), search (a lookup, then the embedding API), and the embedding job, which now asks for both vectors before it touches the database again and writes everything in one transaction, where it used to hold a connection through both calls and every retry of a 429. `hand_back(db)` is the one way to do it: a commit that never raises. **How it is known to be the cause:** with the baseline's own 4 + 15 connections put back, the two rates at which the baseline's plans slowed and stopped arriving (0.4 and 0.8 visits a second) hold, and so does twice that (`docs/loadtest/fix-on-baseline-pools/`): at 1.6 visits a second 3 of the pooler's 4 connections in use at most, 0.6 of the pool on average, where the old code had 18.

254. **The invariant is held by a test on a real database, because it is one statement from being lost.** Any `SELECT` added before a model call brings the bug back, and no unit test of a function would see it. `test_phase30_connections_integration.py` runs a whole plan through the HTTP API and, a tenth of a second into every wait — three models, the extractor's, three tools, the embedding API — asks whether the session of the code that is waiting is in a transaction. It found two things while being written: the three concurrent searches share the run's session, so one's commit is for a millisecond another's "open transaction" (looked at a tenth of a second apart); and the reordered embedding job outlived the test's database cleanup, a deadlock on `TRUNCATE` (the fixture now waits for the app's background tasks).

255. **The Redis pool's limit is a setting too; 100 was nobody's choice.** With the database out of the way the next wall was hit at 3.2 visits a second, exactly where section 4 of the report had put it: every open trip page keeps one Redis connection for as long as it is open, redis-py opens at most 100 and fails the 101st at once, and the app had never said how many it wanted. 137 requests for a plan were answered 500, and 98 finished plans could not be announced — their travellers gave up on plans that were in the database. `REDIS_MAX_CONNECTIONS` (default 100, as before; 500 on the production-like stack) made that rate hold with 135 pages open. It is a larger number, not a different design: at 6.4 visits a second the 500 filled the same way. One subscription a process, handing each page its own trip's events, is the design — left for Phase 31, which breaks Redis under open streams on purpose and will want to change how they are held.

256. **No worker processes were added, and the password check was left on the event loop — both are in the report as what limits it now.** The roadmap names uvicorn workers as a likely fix; nothing in the baseline asked for them — the processor was the last thing to run out, not the first — and a fix for a bottleneck that was not measured is a guess with a deploy attached. After the changes one process holds 3.2 visits a second at 0.61 of a core and stops coping at 6.4 at 0.93: about five visits a second a process. Workers are the next step and not a free one — `/metrics` and its gauges, the tool server's count for each provider's rate limit (`rate_limiter.py`: 30 a minute would become 30 a worker), and the pools are all per process, and the first two would be wrong in silence. Half of that core is bcrypt, 190 ms a sign-in during which the process does nothing else — the whole of the 200 ms request p99 at every rate that holds. Moving it to a thread is a third finding and would have needed a third round of measuring; it is written down with the number that would prove it, not slipped in unmeasured.

257. **The baseline's connections can be put back with one flag.** `python scripts/loadtest.py up --small-pools` lays `docker/loadtest/small-pools.yml` over the stack: 4 at the pooler, 5 + 10 in the app. It is how the code change was told apart from the configuration change, and it stays so that the next change to how a run uses the database can be asked the same question — does it still fit in four connections? The production-like stack itself keeps the 90 and the 40: Phase 27's check passes on them unchanged.

## Phase 31 — Chaos Engineering: Agent Failures

Four things the app depends on were broken on purpose while it planned a trip, on the production-like stack with the stand-ins of Phase 30: the tool server killed, Gemini answering 429, the builder's model never answering, Redis killed under open event streams. `docs/chaos-report.md` has what was expected, what happened and what was changed; `docs/phase31_build_log.md` the rest. Not on a deployment: there is none, and none of this may be done to one.

258. **Things are broken from outside the app; nothing in `src/` can be told to fail.** A fault switch in the app — `CHAOS_KILL_REDIS=1`, a route that raises — is the kind of switch Phase 30 refused for the stand-ins (#240), with a worse accident waiting behind it. So: a process is killed with `kill -9`, a container with `docker kill`, and a model call goes wrong because the *far end* does. Which model, and how, is a file in the load test's container (`/tmp/standin-faults.json`), read by the stand-ins each time a model is made — it can begin and end while the stack runs, and needs nothing an exercise might itself have broken (not Redis, not the database). A test reads all of `src/` for any mention of it.

259. **A model fault is the provider's own client talking to a server that fails — not a stand-in that raises.** The obvious way to make "the builder's model times out" is a stand-in that sleeps and raises a timeout. It would have tested my idea of what the client does. With a fault on, the stand-in hands back the real `ChatGroq` or `ChatGoogleGenerativeAI`, made with exactly the options the app passed, pointed at `loadtest/standins/fault_server.py` — which says 429 in Gemini's words (quota exhausted, "retry in 36s"), 429 in Groq's (`Retry-After: 2`), 500, or reads the request and never answers. That is how exercise 3 found what no reading of the app's code showed: the LangChain wrapper hands the SDK `timeout=None` when none is given, and the SDK then has none at all (#265). The server answers nothing correctly, and its address is held to this machine like the database's (#240): the real client sends its key with every request.

260. **Each exercise was written down as a hypothesis first, and run once on the app as it was.** The four hypotheses are in the report with the clock's time (07:39), before the script that runs the exercises had been run; the "before" runs (07:44–08:04) were on Phase 30's own image. Two were wrong in ways that mattered — the builder would not have failed after twelve minutes but never; a run under a dead Redis was not untouched but slowed to the length of the outage — and one exercise did not test what it was meant to. All of it is kept. The times are from `date` in the command that wrote each section (the lesson of Phase 30's report, whose times were first written from memory).

261. **A dead tool server is replaced, and the call that found it dead is asked again — once.** The client made its session once and kept it for the life of the process: after one `kill -9` every search failed in milliseconds until the backend was restarted. Now a call that finds the connection gone lets go of the session (the next call starts a server) and asks again itself. Again, because a search changes nothing — it reads a provider, or the cache — so asking twice is safe, and the alternative is a plan with a hole in it for a fault that lasted a second. Once, because a request that kills the server would kill the next one too, and a server that will not stay up must not hold a plan. What the caller is told then is `CONNECTION_REFUSED`, the roadmap's name, whether the server died under the call or would not start: to an agent it is one thing — the tool server could not be reached. `mcp_tool_server_starts_total` counts every start; more than one is a death.

262. **One task owns a tool server from start to end; and its pipe is watched.** Both found by killing the real process under the new code, not a mock. The library's pipes and session are scopes that must be left by the task that entered them: left by another, they cancel the one that entered — whichever request had needed a search first, so, under load, somebody's planning run. A task that does nothing else now enters them, waits to be told to leave, and leaves. And the library fails the requests that are waiting when the pipe closes, but one written a moment later is neither answered nor failed — it waits for ever (seen with a server killed again while being started for three calls at once). So what the server says is passed through something that notices when it stops, and a call waits on that beside its answer. The lock that guards all this is kept per event loop: calls now wait on it, and a lock that has been waited on belongs to its loop.

263. **"Nothing could be searched" is not "nothing was found".** With the tool server dead all three searches failed and the trip ended "No flights, places to stay or things to do were found for Udaipur" — true of the result, false as an account, and it tells a traveller to pick another destination. When none of the three could be *run* (each failed for a reason a retry might mend) the trip fails saying so: nothing is wrong with the trip, try again. A search that ran and found nothing keeps the old sentence. And `CONNECTION_REFUSED` has words in `failures.py` — the page had been showing `MCP client exception: `, with nothing after the colon: the exception that a closed pipe raises has no message.

264. **A plan made without one of its searches says so in the itinerary that is saved.** The roadmap: "continues with partial results (clearly labelled in itinerary)". The page already showed a failed search with its reason and a Retry — to whoever had the page open, from `agent_runs`. The itinerary itself, which is what the PDF is made from and what every later reader has, said nothing. `structured_data.missing` is `[{search, what, why, retryable}]`, in the traveller's words, written by the orchestrator when the plan is saved — and dropped from the model's reply if a model ever writes one, like the other fields that are the planner's to write. The page and the PDF do not show it yet (#270).

265. **The model that writes the itinerary is waited for 20 seconds a read and 30 seconds in all; a build that timed out is not built again.** The builder made its client with no timeout, and "no timeout" turned out to mean none: one unanswered request held a trip `planning` for fifteen minutes, when the exercise stopped waiting. Now the client gets `timeout=20` and one more try (a 429 or a 5xx is worth asking again after what the provider says to wait), and the whole reply — both tries — gets 30 seconds from `asyncio.timeout`, whatever the client is in the middle of. A plan is written in 5 to 9 seconds, so 30 is three times the slowest build measured; and with intent parsing, the searches and the local tips before it, a trip whose builder hangs is marked failed inside the roadmap's 60 seconds. A failed build is normally built again up to three times; one that *timed out* is not — the next would wait as long. The preference extractor's client, which had no timeout either and runs after the plan is already the traveller's, gets 10 seconds and no second try.

266. **A planning run has an end, whatever hangs.** `RUN_DEADLINE_S = 300`: past it the run is stopped, the trip marked and the page told it took too long. Not the fix for the builder — that is #265 — but for the next thing that never comes back and that nobody has thought of: a tool server that is alive and stuck, a provider client with a default like Groq's. A plan takes 10 to 16 seconds and a search may wait a minute for a rate limit (#153), so five minutes cuts off nothing that was going to finish.

267. **A run does not wait on a Redis that is not there.** "A dead Redis must never fail a planning run" held; it also must not slow one. The itinerary is published in pieces as it is written, each publish to a dead Redis spent a second or two reconnecting before it gave up, and a build that takes 7 seconds took 32 — the run lasted as long as the outage. Now after a publish fails none is tried for 5 seconds and a single one is given 2; the two events that end a run are always tried. Nothing is lost by it that was not lost already: pub/sub keeps nothing, and the page reads `GET /status`, which does not need Redis and answered throughout.

268. **Redis being away is a 503 in words, and a trip marked `planning` always gets its run.** `POST /plan` writes the conversation to Redis before anything else, so during the outage it was a 500, "something went wrong on our side" — true, and no help to someone deciding whether to try again. A connection or timeout error from Redis that reaches a request is now answered 503 with `Retry-After` and "nothing is lost — please try again shortly"; any other Redis error is still a bug and still a 500. And the order inside starting a run was: mark the trip `planning`, commit, write two things to Redis, start the run — Redis going between the commit and the start would have left a trip nobody was planning and nobody could. After the commit, nothing stops the run from being started.

269. **A planned trip whose saved state is gone is changed by a full re-plan, not refused.** A refinement runs on the state the last run saved in Redis, and without it answered 409 "Run POST /plan first". That state expires after a day; it is also what a run cannot save when Redis is away as it ends — which #267 made the usual case in an outage, since the run no longer waits for Redis to come back — and what a Redis that restarts empty has lost. The trip has an itinerary in Postgres either way. So: no state and no itinerary is still a 409; no state and an itinerary means the change is carried out the one way that needs none of the earlier searches' results — a full re-plan from the trip as Postgres has it — with the turn counted from `agent_runs`, since the conversation went with the state. The answer says so (`refinement_type: "full_replan"`, and why).

270. **Not done here: one subscription for the whole process; the label on the page and in the PDF.** Phase 30 left "a page costs a Redis connection" for this phase (#255), which breaks Redis under open streams. It did, and the streams behaved: every one ended within seconds of the kill, every page reconnected by its own backoff within ten seconds of Redis returning, `CLIENT LIST` showed one subscribed connection per open stream and none once the pages had gone. Nothing was found that one shared subscription would mend — it is a change of capacity, not of correctness, and it wants a load test before and after, not a chaos exercise. It stays where Phase 30 put the number: 500 connections, a setting. And `missing` (#264) is in the itinerary and in `GET /itinerary`; showing it on the page and in the PDF is a change to the frontend and to the PDF's layout that this phase did not make — the page still shows the failed search and its Retry as before.

271. **A machine that slept voids an exercise's times, and says so.** The first run of the fixed app was made with the laptop's lid closed, on battery: macOS slept in cycles for hours while the script ran. What happened in those runs was right; no duration in them meant anything, and two exercises are *about* durations (failed within 60 seconds; away for 30). `scripts/chaos.py` now uses the load test's check (#248) — the wall clock against the steady one — and writes `asleep_s` and `timings_hold` into every record; the records in `docs/chaos/after/` are from a second run, awake.

## Phase 32 — Chaos Engineering: Data Layer

Postgres killed while a plan is being made — and at the point between the two writes that save one — and the backend killed between saving an itinerary and embedding it; on the production-like stack with the stand-ins, like Phase 31's four exercises and with the same script. `docs/chaos-data-report.md` has what was expected, what happened and what was changed; `docs/phase32_build_log.md` the rest. Not on a deployment.

272. **For chaos, the stack's Postgres keeps its data.** The production-like stack's database lives in memory — "every start is a database nobody has migrated yet" (Phase 27), which is right for a stack that is thrown away. Killed and started again it would come back empty, and an empty database says nothing about a failover: there would be nothing to have lost, and no table for the app to find. The chaos overlay gives it a volume (removed with the stack), so that `docker kill` is what it is in production — a crash, a recovery from the log, the same rows as before.

273. **A pooler turns a short outage into a pause — which three of my predictions had missed.** I expected errors at once, a plan lost and its trip stuck `planning`. PgBouncer keeps a query it has no server for (two minutes, by default) and hands it over when Postgres is back: with Postgres away for 15 seconds every request sent meanwhile was answered, late; the plan in flight stopped between two steps and went on; a plan *asked for* during the outage was accepted and made. Even the statement by which a crashed run marks its trip waited and was run. The predictions are kept in the report as written, beside what happened. What the phase then changed is at the edges of that pause, not the pause.

274. **The driver's own timeout is not set — it was tried, and made things worse.** Nothing in the app bounds how long a pooler may keep a query, so `command_timeout=20` was added as the app's limit. With Postgres away for 45 seconds the nine requests that had been waiting did not fail after 20 seconds each: they all failed at the same instant, three seconds *after* Postgres returned, with a bare `TimeoutError` — a 500 — where before the change they had been answered. asyncpg's timeout takes effect only once the server has answered the cancel request it sends, and a server that is away answers nothing. So it bounds nothing while the database is gone, and turns late answers into errors once it is back. Removed; the record of that run is kept (`docs/chaos/tried/`). What bounds the wait is the pooler's `query_wait_timeout`, the hosted pooler's being the hosted pooler's — a limit of this phase, said as one.

275. **"The database cannot be reached" has a name, and is a 503 in words.** `app/db/errors.py` tells that apart from every other way a statement can fail: the driver's connection errors under SQLAlchemy's wrapper (what the backend logged was a plain `DBAPIError` over asyncpg's "connection was closed in the middle of operation"), a pool with no connection to give, a refused connection. A request that meets it is answered 503 with `Retry-After` — "nothing is lost, please try again shortly" — as Redis being away has been since #268. A statement the database *refused* is a bug and is raised on, to be the 500 it always was, with its report: answered "try again" it would fail for ever and nobody would be told.

276. **A traveller is never shown what was raised.** A run that crashed published `str(exc)` to the trip's page. With Postgres killed as a plan was being saved that was `(sqlalchemy.dialects.postgresql.asyncpg.Error) <class 'asyncpg.exceptions.ConnectionDoesNotExistError'>: connection was closed in the middle of operation [SQL: INSERT INTO itineraries …] [parameters: (UUID(…), …` — the statement and, in its parameters, the plan. Now one of three sentences: the planner lost its database for a moment; planning took too long (#266); something went wrong and has been reported. What was raised is in the log and in the error report, which is where it was already going.

277. **A run that ended without marking its trip goes on trying to.** The crash handler marked the trip in the database from inside the run's own session — the session whose connection had just died. Behind a pooler that statement waits and is run; with the database away longer than the pooler waits, or with no pooler, it raises, and the trip says `planning` with nothing planning it until the backend is restarted. Now it is marked from a session of its own, every three seconds for up to ten minutes while the database is away, and the reason is written as the run's closing row, where `GET /status` reads it for a page that was not open to hear it. A trip is only touched while it is as that run left it — a mark that comes late must not undo a plan the traveller has asked for since. (The label of that row, "Stopped: the server was restarted", became "Stopped before it finished": it is no longer only a restart that writes it.)

278. **The pooler looks for its database again every 5 seconds, not every 15.** After a failed attempt to reach Postgres, PgBouncer waits `server_login_retry` before the next and refuses new queries meanwhile. With Postgres back within three seconds the app could not use it for 11.6; after 45 seconds away, for 13.7 — the roadmap's limit is 10. The app's part was a tenth of a second each time: its connections are to the pooler, which never went away, so the roadmap's question — does `pool_pre_ping` find the dead connection? — did not arise on the stack. (It is asked without a pooler in an integration test: every connection the pool holds is ended at the server, and no request meets one.) The number is the stand-in's; what a hosted pooler waits is its operator's.

279. **Half a save is rolled back by Postgres, and the exercise that shows it stops the right statement.** A plan is saved in one transaction: the itinerary inserted, the trip marked `completed`, one commit. I had the order the wrong way round — and the first version of the exercise, holding a lock that stopped the insert, killed Postgres with nothing written and "confirmed" a rollback of nothing. It now holds the trip's own row in the mode an `UPDATE` of it needs and an insert pointing at it does not (`FOR NO KEY UPDATE`), reads from `pg_locks` that the itinerary has been written and the update is waiting, and kills Postgres there. After the restart: no itinerary, the trip not `completed`. Nothing in the app was changed for it; it is kept as the check that nobody splits that commit in two.

280. **An itinerary is saved together with the row that says its embeddings are owed.** The embedding job is a task of the process that saved the itinerary, and asks the embedding API for two vectors before it writes anything. A backend killed in those seconds left an itinerary with no row in `embeddings` at all — and start-up recovery re-queues itineraries that have a row saying "owed". Nothing would ever have embedded it. The row is now written in the transaction that saves the itinerary, so there is no itinerary that is neither embedded nor on record as waiting to be, whatever dies when. (The itinerary is flushed first: there is a foreign key between the two tables and no relationship between the two classes, so nothing else tells the ORM their order — written in one flush the embedding went first, and the first rebuild with this change failed every plan. A mock database had passed it; the integration suite would not have, and is now run before a stack is rebuilt.)

281. **Start-up recovery that could not look, looks again.** "The app must boot even if the database is unreachable" — so recovery was skipped when it was, and that was the end of it until the next restart: trips left `planning`, embeddings owed. When what stopped it is the database being away it is now tried again every 15 seconds, for ten minutes.

282. **Left as they are.** A backend killed just after saving a plan leaves a `completed` trip whose run has no closing row — the steps after the save died with the process; the plan stands, and the count that found it now allows for it. An embedding that is owed is retried at the next start, not before: a job that fails while its backend lives waits for a restart, as since Phase 14. And no statement is retried by the app: behind a pooler a short outage needs none, and a retry of a write that may have been committed is its own problem.

283. **The embedding API's fault is its stand-in failing.** Phase 31's rule was that a model fault is the provider's own client pointed at a server that fails (#259). What stands in for the embedding API is the one function that reaches it, so there is no client to point anywhere: with the fault on, the stand-in raises. That is enough to ask what this phase asks — is an embedding that could not be made retried after a restart — and says nothing about the embedding client's own retries, which no exercise here is about.
